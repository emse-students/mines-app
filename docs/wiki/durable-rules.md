# Durable rules - what this codebase has cost to learn

Every line here was written after something broke. This is an **index of hard-won constraints**, not
a style guide: nothing is here because it sounded sensible, and nothing is added without an incident
behind it.

**How to use it.** Read the section matching what you are about to touch, then open the page it
points at before writing anything. The rules are deliberately blunt one-liners - they exist to make
you STOP, not to explain. The explanation is always one link away, and the link is the point: this
page is a map of where the reasoning lives, so a section you can read in twenty seconds is a section
doing its job.

**How to add one.** ONE LINE, plus the page carrying its reasoning. If the rule needs a paragraph,
the paragraph belongs on that topical page - put it there and leave the one-liner here. If it needs
no page, it probably needs no rule.

**How to remove one.** A rule dies when the thing it constrains no longer exists in the code, or
when another rule already says it. Neither is a loss: the story stays in `CHANGELOG.md` and the
mechanism on the wiki page. Compressed 2026-08-19 from 1570 lines to this, by moving every surviving
paragraph onto the page it pointed at and deleting the narratives whose code was already gone.

**What stays in `CLAUDE.md`** is the handful of rules that apply to EVERY task regardless of area,
plus the pointer here. Adding a rule there means asking first whether it belongs in a section below.

## MLS state and keys -> [mls-protocol](protocols/mls-protocol.md), [auth](frontend/modules/auth.md)

Everything that touches the device key, the PIN, `mls.bin` or an unlock path is on those two pages.
`desync` = [mls-desync-prevention](protocols/mls-desync-prevention.md).

- **A WARNING THAT CANNOT TELL ITS TWO CASES APART IS NOISE, AND THE FIX IS THE DISCRIMINATOR, NOT AN ENTRY IN AN ALLOWLIST.** `WasmMlsClient::new` warned on every device key arriving with no state beside it: a real loss on a returning device, the ordinary shape of a first enrolment on a new one, and one line for both. So it fired on every fresh client, and the campaign harness grew a needle in `FRESH_CLIENT_NARRATION` forgiving it per row - which is a DISPOSITION, not a fix, and it leaves the line firing where it would have meant something. The fact was already computed one layer up (`resolveDeviceId` finds this device's id or MINTS one) and simply not shared. Carry it (`stateWasExpected`), make it REQUIRED so every off-thread client has to state its case rather than inherit a default, and the line becomes a finding again. [mls-wasm](frontend/mls-wasm.md#statewasexpected-and-why-the-constructor-cannot-work-it-out)

**Key packages, and the two kinds that are NOT interchangeable**

- **WHEN A SERVER PROMISES REUSE, THE BYTES IT REUSES MUST BE BUILT FOR IT - a convention that two layers merely agree on is not a mechanism.** The delivery service serves a device's static `key_package` row to every caller once the one-time pool is empty, and it must, or a device whose pool ran dry becomes permanently un-addable. MLS deletes an ordinary KeyPackage's private bundle at the first Welcome built on it, so the row opened one group and locked the device out of every other peer already holding it: ten groups re-added in one burst on real hardware gave one join and nineteen `NoMatchingKeyPackage`, and the device re-asked for a Welcome for ever. The distinction now lives in the crypto - `last_resort` on the fallback, plain on the pool - through ONE builder taking a flag, because four call sites each minting "the fallback" is four chances to mint the wrong kind. [mls-protocol](protocols/mls-protocol.md#the-two-kinds-of-key-package)

- **A STORE THAT ONLY EVER MINTS IS A LEAK, AND RECONCILIATION IN ONE DIRECTION IS NOT RECONCILIATION.** `reconcilePublishedKeyPackages` purges the SERVER of a prekey whose private key is gone locally, and reads like the pair was covered; nothing ever asked the opposite question, so every bundle the server had stopped publishing was kept for the life of the install. Two callers made it unbounded and neither is exotic - a fresh last-resort package published on EVERY connection, and `republishKeyMaterial` purging the pool and minting fifty more once per 30 s for as long as a `NoMatchingKeyPackage` storm lasts. A phone reached a 19.5 MB `mls.bin`, a 17-second checkpoint and a 22-second unlock. **The estimate that made it sound affordable was wrong by five times** - two docblocks justified the pool size against "each ~400 bytes" and a bundle is 1 936, which is why weighing came before pruning: the same measurement shows fifty sends costing ~0 bytes, eliminating message history as the cause rather than leaving it suspected. **And the prune's signal must be EXPIRY, never "the server no longer publishes it"**: the delivery service deletes a one-time prekey as it hands it out, so absence from the server is exactly what a bundle looks like while a peer is about to send the Welcome built on it, and pruning on that would race a join and lose it. An elapsed `not_after` cannot be ambiguous, needs no round-trip and races nothing. [mls-protocol](protocols/mls-protocol.md#the-two-kinds-of-key-package)

**The send ratchet, and what may replace the client under it**

- **No state replacement may rewind this device's own send RATCHET, and an epoch cannot see that it did** - every such seam needs TWO guards, epoch-monotonic AND not-overtaken-by-a-local-send. [desync](protocols/mls-desync-prevention.md#8-client---no-state-replacement-may-rewind-this-devices-own-send-ratchet)
- **A rule that each call site must remember is a rule the next call site will NOT** - the checkpoint lived at 2 of the 18 call sites reaching a send; it is now inside `BaseMlsService.sendMessage`, which a platform cannot opt out of. [desync](protocols/mls-desync-prevention.md#8-client---no-state-replacement-may-rewind-this-devices-own-send-ratchet)
- **A call site that has to know WHICH PLATFORM it is on in order to persist will get it wrong** - `saveState` means two different things, and a second call site had its own copy of the answer. One seam, every checkpoint through it. [desync](protocols/mls-desync-prevention.md#8-client---no-state-replacement-may-rewind-this-devices-own-send-ratchet)
- **An invariant is not its first implementation - re-read what it actually DEMANDS before paying for it.** "`mls.bin` is never behind a frame that has left" never required durability at send time, and the expensive reading survived two design rounds. [desync](protocols/mls-desync-prevention.md#8-client---no-state-replacement-may-rewind-this-devices-own-send-ratchet)
- **Price both halves before choosing between them - an UNPRINTED metric is a guess.** The estimate was ~80 ms and the truth 1.7 s, and splitting the log exposed a duplicate write no reasoning had found. [desync](protocols/mls-desync-prevention.md#8-client---no-state-replacement-may-rewind-this-devices-own-send-ratchet)
- **When a repair can only be wrong in ONE direction, find out which and lean on it** - over-shooting the burn costs a peer a few unused keys, under-shooting refuses a frame; establishing the asymmetry in the dependency's source is what removed the need for atomicity. [desync](protocols/mls-desync-prevention.md#8-client---no-state-replacement-may-rewind-this-devices-own-send-ratchet)

**At rest**

- **What the device key SEALS, the device key change must RE-SEAL** - and whether forgetting is survivable depends entirely on whether something else still holds it. Before adding an encrypted store, answer: who else holds this, and what happens if this copy dies. [channel-encryption](protocols/channel-encryption.md)
- **A migration branch stamps its OWN version, never `SCHEMA_VERSION`** - stamping the current version claims every migration written after it. When bumping, READ the previous branch's stamp. [mob](frontend/mobile.md)
- **An at-rest envelope change needs a reader for the previous format in the SAME commit - and that only buys the FORWARD direction.** Say so at the commit: **the frontend must not be rolled back past `01bc0a13`.** [mls-protocol](protocols/mls-protocol.md#how-the-state-is-encoded-inside-the-envelope-wp-anr-1-2026-08-11)
- **serde has no `Vec<u8>`** - the generic sequence path is x45 slower and x2 larger, measured. Any NEW byte field uses `byte_compat.rs`. [mls-protocol](protocols/mls-protocol.md#how-the-state-is-encoded-inside-the-envelope-wp-anr-1-2026-08-11)

**Unlock**

- `isValidPin` (>= 4 chars) guards setup, change, recovery AND unlock - one rule, or a lockout. [auth](frontend/modules/auth.md#pin-and-device-key)
- **A status code is an ANSWER, a transport failure is not** - only a 401/403 may log a user out, and `navigator.onLine` never proves reachability. [auth](frontend/modules/auth.md#a-status-parsed-back-out-of-a-sentence-is-a-status-that-was-discarded)
- **Offline unlock is only ever the paths that ALREADY skip the server check online** (biometrics, vault); widening it to the PIN is a security change wearing a UX hat. [auth](frontend/modules/auth.md#offline-unlock)
- **A PATH THAT SKIPS A CHECK SKIPS EVERYTHING THAT CHECK HAPPENED TO CARRY.** `resetRequired` rode on the PIN check, so the two paths that legitimately skip the PIN also stopped asking whether the device was still allowed to exist - and a revocation is not a PIN concern. Enumerate what a skipped call ANSWERS, not what it is named after. [auth](frontend/modules/auth.md#pin-and-device-key)
- **ONE DESTRUCTIVE CONSEQUENCE, ONE IMPLEMENTATION, REACHED BY EVERY PATH THAT CAN LEARN THE FACT.** Three places learn a device is revoked; while the wipe was copied per trigger the copies drifted, and the one missing the MLS teardown was the live-session path that needed it most. [auth](frontend/modules/auth.md#pin-and-device-key)
- **AN ERASURE IS NOT FINISHED WHILE ANYTHING THAT CAN WRITE IS STILL RUNNING - STOP FIRST, DELETE SECOND.** A revoked device wiped every store and the 5 s SYNC_WATCHDOG, which nothing had stopped, rebuilt its MLS database and re-marked ten groups 1.25 s later. `resetMls()` nulls a reference and stops NOTHING; the teardown that already existed for logout is the one that had to run. [auth](frontend/modules/auth.md#erasing-a-revoked-device-and-the-125-s-that-undid-it)
- **A CLAIM ABOUT WHAT IS GONE HAS TO BE READ BACK; THE STEPS THAT RAN ARE NOT EVIDENCE.** "nothing of this device remains" was printed over 8.2 MB. But a delayed re-check is NOT the answer - the same wipe serves a user who legitimately signs back in seconds later, and it would accuse them. [auth](frontend/modules/auth.md#erasing-a-revoked-device-and-the-125-s-that-undid-it)
- **A PLATFORM BRANCH THAT REPLACES A SHARED STEP DELETES HALF THE WORK - ASK WHETHER THE NATIVE PATH IS AN ADDITION.** The factory wipe cleared the native stores OR the WebView's, and every platform has a WebView: a revoked Pixel 6a kept 5.9 MB of `CanariDB_<userId>`. The tell was already in the same function - the cache and localStorage steps sat OUTSIDE the branch, and only the databases had been pulled inside it. [auth](frontend/modules/auth.md#erasing-a-revoked-device-and-the-125-s-that-undid-it)
- **NAMING A STORAGE BACKEND DOES NOT PICK A PATH, IT PICKS A DIFFERENT DEVICE - and a READER doing it creates the store it reads.** A posts panel built an `IndexedDbStorage` by hand, so on a phone it answered from a database nothing writes while the chat answered from SQLite, and `init()` brought that database into existence. `getStorage` is the only place allowed to choose, enforced by `db/backendChoice.test.ts`. [auth](frontend/modules/auth.md#erasing-a-revoked-device-and-the-125-s-that-undid-it)
- **A TEARDOWN THAT CLEARS THE FLAG OTHERS TREAT AS "SOMEONE OWNS THIS" IS THE EVENT THAT STARTS ITS OWN COMPETITOR.** `wipeRevokedDevice` begins by tearing the session down, which sets `isLoggedIn` false - one of the three flags `loginImpl` reads to decide nobody owns the flow. A login started 3 ms after the `device_revoked` frame, could not get its own revocation check answered because the wipe had killed the session, read that as NOT revoked, and reopened the database 24 ms before the delete. **Exclude the whole DURATION, never the identity**: between clearing `mls_device_id_<userId>` and deleting the stores there is a window in which no identity exists to recognise. A latch raised before the first step and released in `finally` is causal, costs nothing and cannot lock a real user out. [auth](frontend/modules/auth.md#erasing-a-revoked-device-and-the-125-s-that-undid-it)

- **`deleteDatabase` DOES NOT FAIL ON AN OPEN CONNECTION - IT BLOCKS, AND THE CONNECTION THAT SURVIVES EVERY WIPE IS THE ONE NO CALLER CAN REACH.** `hex.ts` caches its MLS handle in a module singleton that `removeMlsState` REOPENS one step before the wipe; two databases survived on a revoked device while every step reported success. Close it where it is owned, not through a parameter - and **a parameter documented as necessary that no production call site passes is a comment, not a parameter.** SECOND SITE, 2026-08-30: the same wipe left `CanariDB_<userId>` open, and the reason it recurred is that **`getStorage()` is a FACTORY - so the number of connections is the number of READERS, not one**, and only the session's is reachable afterwards. A module that hands out connections owns a REGISTRY of the ones it has open; anything else can close exactly the handle the caller already had. [auth](frontend/modules/auth.md#erasing-a-revoked-device-and-the-125-s-that-undid-it)
- **A BEST-EFFORT STEP THAT CAN KILL THE PROCESS IS NOT BEST-EFFORT, AND EVERY STEP AFTER IT IS ITS HOSTAGE.** `wipeDeviceToFactory` catches per step, which covers every failure a promise can carry - and its biometric step raised an ANDROID ACTIVITY that failed to inflate, so the process took `SIG: 9` 55 ms after `[RESET]` and the WebView was never touched. Ask of each step what its WORST failure is, not whether it is wrapped: the one that can end the process runs last, and the fix belongs at the step. [auth](frontend/modules/auth.md#erasing-a-revoked-device-and-the-125-s-that-undid-it)
- **A WIPE MUST NOT BE REFUSABLE BY WHOEVER IS HOLDING THE DEVICE.** The revocation wipe called `BiometricService.disable()`, whose whole contract is a prompt that can be cancelled - right for a Settings toggle, backwards for a device its owner declared lost, because the person at the sensor may be whoever took it. And check what the step actually DELETES: that one passed no alias, so `deleteKeyBytes` was never called and "the biometric key" cleared two flags. [auth](frontend/modules/auth.md#erasing-a-revoked-device-and-the-125-s-that-undid-it)
- **A TOTAL WIPE'S ALLOWLIST IS OF WHAT SURVIVES, AND ITS DEFAULT IS DELETE.** The general rule that a destructive control needs an allowlist of what it MAY touch inverts here: `clear_app_data` named what it deleted - `extension() == "db"` - so every file added to the app data directory after it was written survived unmentioned, and a revoked phone kept `graine_seeds.json`, `channel_keys.json`, `pending_push_secret.txt`, the key-alias index and six cached faces. Nothing reports this: the wipe logs success, and only reading the disk disagrees. Name the framework's directories and delete the rest. [auth](frontend/modules/auth.md#erasing-a-revoked-device-and-the-125-s-that-undid-it)
- **A DEVICE WITH TWO STORES IS WIPED BY TWO OWNERS, AND EACH MUST NAME THE OTHER'S TERRITORY.** The native sweep must not touch `app_webview` (the engine is reading out of it - that is the `SIG: 9` above) and the WebView sweep cannot see `mls.bin`. Neither half is a fallback for the other and neither may be widened into the other's: the two constants that draw the border, `KEPT_AT_TOP_LEVEL` in `commands/storage.rs` and `OUR_NATIVE` in the harness's `phone.mjs`, are written facing each other on purpose. [auth](frontend/modules/auth.md#erasing-a-revoked-device-and-the-125-s-that-undid-it)
- **A QUESTION WHOSE ANSWER DESTROYS SOMETHING TAKES ITS SUBJECT AS AN ARGUMENT, NEVER FROM AMBIENT STATE.** `isDeviceRevoked()` read fields that are `unknown`/`pending` until `init()` runs, so asking before init would answer "not revoked" for a reason having nothing to do with revocation - a wrong answer no caller could see was wrong. [auth](frontend/modules/auth.md#pin-and-device-key)

## Community channels -> [chat](frontend/modules/chat.md), [social-service](services/social-service.md)

Deep links, system events, rosters and the channel/DM asymmetry are on those two pages;
`rework` = [community-rework](services/community-rework.md),
`graine` = [channel-encryption](protocols/channel-encryption.md).

- **A LISTING HAS NO AUTHORITY OVER A FACT CREATED AFTER ITS REQUEST WENT OUT.** A reconciliation that deletes whatever the server did not mention is right only about the moment it asked, and the workspace load spends SECONDS between the two - it joins a key group and lists the salons of every community before it prunes. A community created in that window was absent from an answer already in flight, and was deleted for it, together with the salon just made inside it: measured on prod, the community left the rail 1.5 s after it was created and the app dropped the user into an unrelated one, silently, so every gesture afterwards went to the wrong community. **Date the snapshot against local creations - a monotonic tick, never a clock** - and let the prune act only on what existed when it asked. Absent and not-yet-born are different facts. **AND IT HAS A THIRD SITE, FOUND 2026-08-30 - the MLS purge in `discoverMissingGroups`, which is worse because what it deletes cannot be re-fetched.** It read the LOCAL set after awaiting the server list, so a group created during the fetch was absent from the snapshot by construction; the creating device held the only copy of the tree, so forgetting it left every member counted by the server and unable to ever join - `getGroupMeta` still answered ok and re-entry was refused `no_base_published`. `initializeConnection` had taken both reads at one instant since WP-GRAINE-1 and said so in a comment, and the second copy of the decision did not. **Capture the local side BEFORE asking, at every site that prunes** - and note the asymmetry that makes it free: capturing early can only SPARE, because a group that really did go away is swept on the next pass. [chat](frontend/modules/chat.md) **AND A FOURTH SITE, THE SAME DAY, TAUGHT THAT ORDERING THE READERS IS NOT ENOUGH.** `initializeConnection`'s sweep had the identical inversion and was cleared by the first audit because its COMMENT claimed both reads happened at one instant while the code read the local set after awaiting the server list - so the prose was audited and the code was not. It destroyed a group 291 ms old. The deeper fault was in the WRITE: `createNewGroup` registered the local MLS group BEFORE the membership that makes it appear in the server list, so the window existed for every reader to fall into, present and future. **Where a fact must be visible before a thing is observable, establish it in that order at the WRITE, and the window stops existing rather than being dodged by each reader in turn** - a discriminating extra read would not have saved this one, because the membership it would have consulted is written by the very call that had not run yet. [chat](frontend/modules/chat.md)
- **A PATH THAT TOLERATES A PARTIAL FAILURE MUST STILL REFUSE TO ANNOUNCE THE WHOLE AS A SUCCESS.** Group creation catches around the bulk add on purpose: one device's Welcome failing is not a reason to abort a group, and that device recovers through its own `welcome_request`. The same catch also swallowed the group's OWN disappearance, and 68 ms later the console said `[OK] Group created.` over state that no longer existed - a conversation shown as working whose every member, the creator included, was locked out for ever. **Before announcing, assert the thing the announcement claims, as a FACT and never as the absence of an exception** (`getLocalGroups().includes(id)`, not the text of a caught error). A tolerance is a statement about WHICH failures are survivable; it is never a licence to stop checking that the object exists. [chat](frontend/modules/chat.md)
- **A CREATION IS A GRANT, AND EVERY GRANT ANNOUNCES ITSELF.** Three paths put a user into a private salon's `allowedUsers` - an accepted invite, an admin join, an added member - and each publishes `channel.member.joined` to `channelAudience` AFTER the write, so the newly-admitted person is inside the audience rather than the one it misses. Creation told nobody, including the creator's OWN other devices, and the only other way into a private salon's distribution group is a full workspace load (post-login, the `online` event, a deep link). So a second device already running joined nothing and could not decrypt a word of the salon until it was relaunched. Measured by COMM-25 on prod: the phone joined the group of all three salons that existed when it loaded its workspaces and never heard about the one created nine seconds later. **When a set of paths writes the same field, the announcement belongs to the FIELD, not to the path** - enumerate the writers, never the ones that already announce. [social-service](services/social-service.md)
- **WHATEVER CREATES A THING PREPARES IT, because the creator is the first to USE it.** Creating a community dropped you into its first salon with the composer ready, and the first message was refused: a public salon seals to the COMMUNITY's group, and the only paths that ever ensured that group were the workspace LOAD and the creation of a PRIVATE salon. Preparation deferred to "the next load" is preparation that is missing for exactly the window in which the object is newest - and it HEALS, which is what hides it: a reload fixed it, and so did the first person joining. [graine](protocols/channel-encryption.md)
- **HOLDING A THING IS NOT BEING ALLOWED TO USE IT, AND A COMMENT CANNOT MAKE IT SO.** Two devices that both find a salon's distribution group uninitialised both create it; the server's first-publish INSERT decides, and the loser discards its group. `ensureDistributionGroup` claimed that cost nothing because "this runs before any seed is sent" - true of that CALL, and of nothing else. For the width of the publish the doomed group is in `getLocalGroups()`, so `distributionEpochFor` - which asks "held?" and means "usable?" - answered epoch 0, and a concurrent message minted a Graine session against a group about to be thrown away. The session died with it and the message was unreadable by its own author; the frame classifies as `unknown`, is never acknowledged, and came back on every later row, so ONE race left two rows vacuous and fifteen dirty. **A provisional state is a THIRD state: give it its own name, make it as narrow as the window it describes, and clear it on every exit.** An invariant only a comment asserts is one the next concurrent caller gets to disprove. [graine](protocols/channel-encryption.md)
- **AN ELECTION HELD IN ONE BRANCH IS NO ELECTION AT ALL, and the branch it forgets is the ORDERING NOBODY TESTED.** The first-publish race between two devices creating one distribution group was decided by `ON CONFLICT DO NOTHING` - correct, and reached only when the two INSERTs actually collide. Serialized, the second publisher found a row and fell through to an UPDATE guarded on `baseEpoch <= :baseEpoch`, so epoch 0 replaced epoch 0 and BOTH writers were told `stored: true`; the client had always known how to discard a lost race and was simply never told it lost. Measured on prod by COMM-8: three `epoch=0 stored=true` publishes for one group inside one second, and the creator that minted the salon's only Graine session orphaned at epoch 0, refusing the group's own first commit as `InvalidSignature` while `epoch gap [msg_epoch=4, group_epoch=0]` repeated 514 times - a seed with `no reachable holder`, unrecoverable by design. **State the rule at every guard that can decide, and have each report what it MATCHED rather than what it attempted** - a read before a write cannot be trusted under concurrency, so the `WHERE` has to carry the same predicate. And an equality accepted "just in case" is a claim about who else writes: enumerate the republishers and prove each carries a strictly newer value, or the tolerance IS the hole. [graine](protocols/channel-encryption.md)

**Governance, and controls that destroy**

- **A RULE THE SERVER ENFORCES AND THE CLIENT HAS NEVER HEARD OF IS HALF A FEATURE** - the refusal is correct and the product still offers the control, so the person reads a 403 as a broken app. Send the DECISION, never the policy: a client holds none of the inputs (roles, permissions) the rule needs, so handing it the policy buys a second copy of the rule with half its arguments missing. `writePolicyAllows` is the only definition, read by `canWriteToChannel` and by the workspace listing. [social-service](services/social-service.md)
- **A DECISION SENT ONLY IN A LISTING IS A DECISION THE PERSON ALREADY IN THE ROOM NEVER GETS.** Teaching the listing to answer `viewerCanWrite` fixed COMM-7 for whoever loaded the community AFTER the change and for nobody else - the second run failed identically, because the device changing a rule is never the device holding the stale one. **A rule that can change while somebody is looking at it owes an announcement, and the announcement carries the DECISION** - so the audience is SPLIT BY THE ANSWER and each half addressed with its own verdict, since one payload cannot carry a per-viewer answer. Absent means UNCHANGED on the receiving side: a rename reuses the same event and must not silence a composer. [social-service](services/social-service.md)
- **TWO EDITS THAT COMMUTE MUST BE SENT AS THE OPERATIONS THEY ARE, NEVER AS THE STATE THEY PRODUCE.** A permission-grid cell IS a delta - grant this one key - and it was sent as the role's whole list, computed from what that browser held. Two administrators toggling two DIFFERENT keys of one role therefore did not race: the second write carried a list built before the first landed and erased it, and the loser's grid kept showing a permission the server had dropped AND one it had never stored. Optimistic concurrency would have been the other answer and a worse one - it turns two compatible edits into a conflict a person has to resolve. **A whole-state write is only honest when the writer owns the whole state.** Found on prod by COMM-20 on its first run. [social-service](services/social-service.md)
- **Every operation checks what the ACTOR may do; ask also what the SYSTEM would be left as.** Five paths removed the last admin - one absent postcondition seen from five sides, so guarding any one left the hole open. Enumerate the sides by asking what else WRITES the table. [rework](services/community-rework.md#axis-2---a-community-can-never-be-left-ungoverned---shipped-2026-08-18)
- **Enforce it as a REFUSAL wherever refusing is possible, and add no repair route** - making the broken state unreachable beats a destructive button that restores it. Where refusal is impossible, the repair is DETERMINISTIC, never a heuristic and never a clock. [rework](services/community-rework.md#axis-2---a-community-can-never-be-left-ungoverned---shipped-2026-08-18)
- **Recoverability that only recovers UNREADABLE rows is not recoverability** - when a soft delete's justification is the restore, re-ask whether the restore still produces something usable. **A SOFT DELETE THAT DESTROYS THE KEY IN THE SAME CALL IS A HARD DELETE THAT LIES**: it keeps the rows and throws away the only thing that made keeping them worth anything. [social-service](services/social-service.md#deleting-a-community-is-irreversible-and-the-gate-is-a-server-argument)
- **A RULE FIXED AT ONE SCOPE IS OWED TO EVERY SCOPE SHARING THE MECHANISM, and the smaller one is where nobody looks.** The community's soft delete was made real on 2026-08-18; the SALON's, one level down, same argument word for word, survived two more days and was found by a test asking whether the row was gone. When a finding is written as a sentence about a mechanism, enumerate what else runs that mechanism before closing it. [social-service](services/social-service.md#deleting-a-channel)
- **Turning a reversible control irreversible changes what every DEPLOYED client is saying - so go and READ what they say.** Where their wording promised the old meaning, the gate is a new argument they do not send, and they fail closed. Where it already promised the new one, adding an argument breaks working clients for nothing: `deleteWorkspace` needed `confirmationName`, `deleteChannel` needed no gate at all, because its dialog had said "definitivement" since the first version that shipped. **The rule is the reading, never the token.** A confirmation only the dialog enforces is a decoration. [social-service](services/social-service.md#deleting-a-channel-took-no-new-argument-deliberately-2026-08-20)
- **A link nobody can ENUMERATE is not revocable** - one live invite, rotation the only way to mint, and the bounds shown next to the token. [rework](services/community-rework.md#axis-3---an-invite-is-one-link-bounded---shipped-2026-08-18)
- **An action may only mutate state at its OWN scope** - an operation the model cannot express must be REFUSED, never approximated with the neighbouring scope's write, and `{ success: true }` that removed nothing is a lie. **Unmanageable is worse than gone.** [social-service](services/social-service.md)

**The key-distribution group, which is not a conversation**

- **A RULE READ AT TWO MOMENTS MUST BE GATED AT BOTH, and the second moment is where nobody looks.** `historyVisibility` was stored, broadcast, narrowed fail-closed and enforced on the join-time bundle - and the seed-REPAIR path, which no reader of that feature ever opens, handed the same past back one session id at a time, so a community that chose "rien de plus ancien" got the opposite. **Enumerate every place the guarded thing LEAVES, not every place the feature is mentioned**, and give the rule ONE module both callers read so the two readings cannot drift again. Found on prod by COMM-12; unreachable from the repository, because each path was correct in isolation. [graine](protocols/channel-encryption.md#wp-3435-and-the-rule-the-server-cannot-enforce)
- **AN INVARIANT THAT HOLDS "EVENTUALLY" DOES NOT HOLD AT THE INSTANT A GUARD READS IT.** The first fix withheld any seed minted before a member arrived, reasoning that a join advances the distribution group's epoch and rotation follows - true, but rotation is decided by the SENDER from the epoch it has PROCESSED, and a join is an EXTERNAL commit it learns of late. So a session spans the arrival and the guard withheld messages the member was entitled to. **A boundary drawn across a window somebody else closes must be drawn INSIDE the window's units** - here `firstIndex`, which already existed for it - and the same run that found the first defect is what found this. When a rationale says "by construction", name the actor that performs the construction and ask when. [graine](protocols/channel-encryption.md#wp-3435-and-the-rule-the-server-cannot-enforce)
- **WHEN TWO DEVICES MUST AGREE ON A NUMBER, HAVE THE SERVER COMPUTE IT.** The history floor compares a member's arrival with each message's date; both are server columns written by one clock, so asking the server removes every device clock from the decision and makes each answerer arrive at the same number. A client-side comparison of a server-stamped arrival against a peer's device-stamped mint time would have been sharp only to that peer's skew - correct almost always, which is the worst kind. [graine](protocols/channel-encryption.md#wp-3435-and-the-rule-the-server-cannot-enforce)
- **AN ADD-IF-ABSENT ON A REFRESH PATH DISCARDS THE REFRESH, SILENTLY AND FOR THE WHOLE SESSION.** `addChannelToWorkspace` ignored a channel already in the sidebar, and the full re-read from the server calls it for every channel it just fetched - so an entry kept whatever it was created with. It hid the administrator join: the server answered `viewerHasAccess: true`, and the row went on offering "Rejoindre" for ever. **When a function is reused by a REFRESH, "already there" means UPDATE, not skip** - and the update MERGES, because a field the reload does not carry (`unreadCount`) must not be erased by one that does. Found on prod by COMM-13, whose four other assertions all passed: the join was complete everywhere except on the screen of the person who performed it. [chat](frontend/modules/chat.md)
- **A LIST IS AUTHORITATIVE ONLY FOR THE POPULATION IT WAS WRITTEN TO ENUMERATE.** `getUserGroups` answers for CONVERSATIONS and excludes a community's distribution group deliberately; two reconcilers read it as "every group this device may hold" and destroyed that group on every connection, checkpointing the loss - so nobody could send in any community. Absence from a list is a reason to ASK, never a reason to destroy. [graine](protocols/channel-encryption.md#9-the-distribution-group-is-not-a-conversation-and-two-sweeps-assumed-it-was---fixed-2026-08-19)
- **The sweep that would have destroyed a thing is where it should LEARN what the thing is** - one row read, the discriminator registered, and every later sweep in the session answers locally. That is what removes the race, not an ordering between two async paths. [graine](protocols/channel-encryption.md#9-the-distribution-group-is-not-a-conversation-and-two-sweeps-assumed-it-was---fixed-2026-08-19)
- **NOT ACKNOWLEDGING IS ONLY RIGHT WHILE REDELIVERY CAN STILL HELP.** A frame the crypto layer already classified as unreadable for good - a past epoch, a spent generation, this device's OWN frame - comes back for ever if the refusal is blanket. Classify at the throw and acknowledge the permanent ones; a lost seed is recovered by ASKING a peer, never by a redelivery. [graine](protocols/channel-encryption.md#9-the-distribution-group-is-not-a-conversation-and-two-sweeps-assumed-it-was---fixed-2026-08-19)
- **A CLASSIFIER IS ONLY INSTALLED WHERE THE ERROR IS STILL TRAVELLING.** DEL-10's whole mechanism - the owed exit written before the call, cleared only by an ANSWER, replayed on reconnect - shipped correct and measured nothing for three days: `exitGroupAndCleanup` classifies what its `serverAction` throws, and `deleteGroupAndBroadcast` / `leaveGroupAndBroadcast` each caught the exit failure in their OWN step 2 first (one logging and moving on, one a bare `catch { /* non-blocking */ }`). So nothing threw, the classifier never ran, and the happy path's `clearPendingGroupExit` deleted the row written three lines earlier - every stated property holding over a store empty by the time anyone read it. Prod, `4a79a6c6`: one DELETE sent, none answered, `drainStarted: false` and `exitLines: []` on both reconnects, the group still live in `dm_groups`. **Enumerate the frames between the THROW and the reader** - one `catch` anywhere between them makes the reader unreachable while every test of the reader still passes, and a `console.error` carrying `Failed to fetch` is forgiven as the noise of a deliberate cut, so the swallow is silent twice over. Hold the failure, finish the unconditional local work, rethrow last. [chat](frontend/modules/chat.md#an-exit-is-owed-to-the-server-and-the-local-purge-is-not-what-pays-it-del-10)

**When somebody leaves**

- **A PREMISE STATED IN A DOC-COMMENT IS NOT A MECHANISM.** Graine's rotation fired on an epoch that changed, and its own doc said "every membership change commits to the distribution group and advances its epoch". Nothing did. When a security property rests on a sentence, go and find the code that makes the sentence true, or write it. [graine](protocols/channel-encryption.md#10-a-departure-moved-nothing-and-rotation-waited-on-it---fixed-2026-08-19)
- **REVOCATION HAS TWO HALVES AND THEY ARE NOT SYMMETRIC.** Routing is revoked server-side, immediately, with nobody online; the cryptographic half is a commit only a remaining member can produce, so it is lazy. Do the server half FIRST and let it abort the removal: the lazy half self-heals on the next load, a routing row left behind never does. [graine](protocols/channel-encryption.md#10-a-departure-moved-nothing-and-rotation-waited-on-it---fixed-2026-08-19)
- **A DIFF CONVERGES WHERE AN EVENT RACES.** A departure notice reaches only who is online and only one of them may act; a diff between two authoritative lists is the same answer whoever runs it, whenever, and ends at "nothing to do". Prefer it to an elected committer or a durable "somebody left" marker. [graine](protocols/channel-encryption.md#10-a-departure-moved-nothing-and-rotation-waited-on-it---fixed-2026-08-19)
- **THE TREE IS THE AUTHORITY ON WHO CAN READ; A ROUTING TABLE ANSWERS WHO GETS SENT TO.** They are different questions, they disagree (a fresh-started device empties its rows while its leaf stands), and a removal decision that reads the second locks out members it should keep. [graine](protocols/channel-encryption.md#10-a-departure-moved-nothing-and-rotation-waited-on-it---fixed-2026-08-19)
- **AN IDENTIFIER THAT IS A PREFIX OF ANOTHER NEEDS THE SEPARATOR IN THE COMPARISON.** `remove_members_for_users` compared a bare user id with a `userId:deviceId` credential and matched nothing at all - a whole removal path inert, with no test, for as long as it existed. Compare against the shape the value actually has. [graine](protocols/channel-encryption.md#10-a-departure-moved-nothing-and-rotation-waited-on-it---fixed-2026-08-19)

**Two messaging systems, one product**

- **A CHANNEL AND A DM MUST FAIL THE SAME WAY, or the difference teaches the user something false.** Graine's §4.5 required a "unreadable, key on the way" placeholder that MLS DMs deliberately do not have: an unopenable frame is logged, reconciled and never shown. The doc was corrected to the code, not the reverse - and a placeholder added to one of the two now has to be added to both. When a rule about presentation is written for ONE of them, go and read what the other does before writing it. [graine](protocols/channel-encryption.md#45-a-missing-seed-is-requested-and-said-out-loud)

**Who an event is ADDRESSED to**

- **AN AUDIENCE IS DERIVED FROM ACCESS, OR IT IS NOT AN ACCESS CONTROL.** Every channel event was published to `getWorkspaceMemberIds` - a question about the CONTAINER - while `canAccessChannel` only ever ran on the ACTOR. A private salon's ciphertext, typing, pins and tallies went to members the same server refuses over REST, who already held the seed. Ask of every fan-out which question its recipient list answers. [graine](protocols/channel-encryption.md#11-a-private-salons-ciphertext-was-addressed-to-the-whole-community---fixed-2026-08-19)
- **THE PATH THAT LOOKS RISKY GETS READ; THE ONE THAT LOOKS LIKE PLUMBING DOES NOT.** Push filtered correctly because it was written per recipient and reached for the guard naturally; the WebSocket fan-out, three lines away, did not. When one of two paths to the same data is right, that is evidence about its AUTHOR, never about the other. [graine](protocols/channel-encryption.md#11-a-private-salons-ciphertext-was-addressed-to-the-whole-community---fixed-2026-08-19)
- **A RULE WITH THREE IMPLEMENTATIONS HAS A FOURTH PLACE THAT NEEDED IT AND HAS NONE.** Channel readability was hand-rolled in the guard, in the roster listing and in the push loop - and absent from the audience. Extract it PURE, with the expensive lookup passed in, so each caller supplies it from what it already holds. [graine](protocols/channel-encryption.md#11-a-private-salons-ciphertext-was-addressed-to-the-whole-community---fixed-2026-08-19)
- **DERIVING AN AUDIENCE FROM ACCESS MAKES ORDER LOAD-BEARING AT EVERY MOMENT ACCESS CHANGES.** Grant BEFORE announcing, or the invitation reaches everyone but the invitee; revoke BEFORE announcing and add the subject back BY NAME, because losing access is the one event its subject must receive. [graine](protocols/channel-encryption.md#11-a-private-salons-ciphertext-was-addressed-to-the-whole-community---fixed-2026-08-19)
- **SERVER-ENFORCED AND END-TO-END ARE DIFFERENT GUARANTEES, AND A PRODUCT MAY ONLY CLAIM THE ONE IT HAS.** A private salon's seed rides the COMMUNITY's distribution group, so every member holds the key; scoping the fan-out stops the server handing over the ciphertext and nothing more. Say which of the two a feature has, in the protocol page, before anyone infers the stronger one. [graine](protocols/channel-encryption.md#11-a-private-salons-ciphertext-was-addressed-to-the-whole-community---fixed-2026-08-19)

**Two clocks, and the answers derived from them**

- **Two windows meant to be one will DRIFT: derive the second from the first, never re-time it** - and a second copy of the number cannot know about the EXCEPTIONS. The device asks which sessions still have messages and forgets the rest. [graine](protocols/channel-encryption.md)
- **A derived answer must not conflate "gone" with "not there YET", nor with "NO ANSWER"** - the age check separates the first pair, failing closed separates the second. Both are tests. [graine](protocols/channel-encryption.md)

**Small ones that keep costing**

- Never return a `Channel` entity to a client: it carries `masterSecret`. Project fields explicitly. [social-service](services/social-service.md)
- `/c/<groupId>` and `/chat/<groupId>` are NOT routes; a conversation opens by publishing to `notifNav`. [chat](frontend/modules/chat.md#deep-linking-into-a-channel)

## MLS membership and routing -> [mls-protocol](protocols/mls-protocol.md), [chat-delivery](services/chat-delivery.md)

`mls` = [mls-protocol](protocols/mls-protocol.md), `cd` = [chat-delivery](services/chat-delivery.md),
`hr` = [history-reconciliation](protocols/history-reconciliation.md),
`chat` = [chat](frontend/modules/chat.md).

**Who may do what, and who is told**

- **THE RECORD THAT MAKES AN AUTHORITATIVE WRITE SURVIVABLE FOR EVERYBODY ELSE MAY NOT BE BEST-EFFORT.** The commit-log insert sat outside the transaction that had already advanced `activeEpoch`, behind a `catch` -> `warn`, reasoned as *"storing is best-effort: a failure must not undo the accepted epoch advance"* - the inversion IS the defect. `(groupId, baseEpoch)` is UNIQUE, so the row skipped can never be written by anybody: epoch 121 of DM `7da231f8` is absent from a log running 0..129 and every device stopped there is stranded for the life of the group. The same hole had a second entrance, a commit carrying no `proto` advancing the epoch and recording nothing at all. **A write whose only purpose is to let others catch up shares the fate of what it describes, or the catch-up is a fiction.** [cd](services/chat-delivery.md)

- **CONTIGUITY IS WHAT A REPLAY NEEDS, AND "IS THE FLOOR TOO HIGH" IS A DIFFERENT QUESTION.** `getCommitsSince` computed `belowFloor` for a gap at the START and returned every row above `sinceEpoch` untouched, so a hole in the MIDDLE was discovered by applying the prefix, throwing on the next commit, freezing the outbox and waiting out a 30 s watchdog - during which every arriving frame was ACKed and dropped. The server held the answer in the response it was already writing. **A terminating answer is carried, not discovered by failing** - and PRUNING and a HOLE must stay separate, both ending rung 1 but only one of them accusing anybody. [cd](services/chat-delivery.md)

- **A BEST-EFFORT FOLLOW-UP TO A DURABLE WRITE IS ONLY ACCEPTABLE IF ITS LOSS IS DETECTABLE BY SOMEBODY WHO CAN UNDO IT.** The commit that advances an epoch is transactional; the publish that lets everyone ELSE reach that epoch was `void refreshGroupInfo(...)`, and its own comment admitted the loss was permanent. It was: four of forty-three groups measured stale on production, every one by EXACTLY ONE epoch - the signature of one lost follow-up, not of drift - two of them for five days with three devices locked out. **Putting the follow-up on the critical path is not the fix** (a commit that succeeded must not report failure), and neither is a client-side owed-work queue: the server's own two columns already ARE the durable record of "a republish is owed", authoritative and answering exactly that question, so a second copy could only go stale. What makes it survivable is that the fact travels on a read the repairer ALREADY performs, and that the repairer is the only kind of party that can act - here, a member holding the tree, on the one call every device makes on every connection. **Never let a repair need a trigger the mechanism does not already have.** [mls](protocols/mls-recovery-ladder.md)

- **A LOCAL BELIEF IS NOT EVIDENCE ABOUT A REMOTE FACT, AND THE PARTY HOLDING THE PROOF MUST BE THE ONE THAT ACTS.** Three mechanisms could have repaired a device whose tree the server held no leaf for, and all three asked `getLocalGroups()` - which answers *"do I hold a tree"*, never *"does the server accept me as a member"*. So a device with a perfectly well-formed tree for a roster seat nobody ever honoured was skipped by the connection sync, skipped by `requestReAdd`'s own guard before it could reach the `pending` discriminator written for exactly that population, and had its recovery bookkeeping CLEARED every 5 s by the SYNC_WATCHDOG *because* the WASM held the group. Measured 2026-09-04: eight messages at attempt 18-23, a `pending` row two and a half hours old, surviving a full page reload. **The only party that could see it was the sender** - the server's `SenderNotActive` refusal is the sole proof that a tree one HOLDS is worthless - and the outbox classified it correctly, logged a line naming the livelock, and then re-posted the same frame for ever. **Observing a defect is not repairing it: a component that holds a proof no one else can obtain owes the repair, not a log line.** [mls](protocols/mls-recovery-ladder.md)

- **"TRANSIENT" IS A CLAIM ABOUT THE FUTURE, AND A RETRY LADDER IS NOT ALLOWED TO MAKE IT BY DEFAULT.** `SenderNotActive` fell through to the same `catch` as a network blip and was logged `transient failure (attempt 23)` - a sentence that is true of a 502 and false of a server that has refused this device's leaf and will refuse it identically until somebody re-admits it. The two arms share the backoff because the MESSAGE must be kept either way; they must not share the LINE, because a reader who learns that "transient failure" means "ignore" is the reader who misses the one that means "nothing will ever fix this". **Say what is being retried and what is being waited on - here the message and the repair - and never let a permanent condition inherit a transient condition's vocabulary.** [chat](frontend/modules/chat.md)

- **A REPAIR THAT WRITES BEFORE ITS OWN PREREQUISITE HOLDS CAN MANUFACTURE THE FAULT IT CLEANS UP.** `kickStaleLeaf` removed a stale leaf from the TREE and cleared the device's ROUTING ROW unconditionally, so a refused Remove still wrote `pending`. Harmless while `pending` only meant "wait"; the day `pending` with nothing owed came to mean "join by external commit", the same write started inviting a SECOND leaf beside the live one - the duplicate-leaf race, reached from the repair side. **Fixing one half of a mechanism re-prices the other half**, so re-read what the changed value now authorises. And "nothing to remove" is not a refusal: a tree that never held the leaf is the outcome asked for, which is why it is a TYPE (`MlsError::NoSuchMember`) and not a substring of an OpenMLS message. [mls](protocols/mls-protocol.md)

- **A STATE READ AS AN EVENT IS A WAIT WITH NO END, AND THE DISCRIMINATOR IS USUALLY ALREADY ON THE SERVER.** `status = 'pending'` on a device membership means "a member has been TOLD to Add this device" and nothing about anyone doing it - yet the client's recovery read it as "an Add is in flight, a Welcome is owed", so a device signing in with no other member online asked once a minute for ten hours while every group it wanted had a usable external-join base. Two facts separate the situations the column collapses, and both were already computed server-side: a `queued_message` carrying a Welcome for THIS device and THIS group, and the group's add lock held RIGHT NOW - the second being the only thing covering the interval between the roster row and the queued Welcome, which is where a bare `&& welcomeQueued` re-opens the duplicate-leaf race. **Before making a party wait, name what would end the wait and ask whether that thing exists**; carry the answer to the decision point rather than letting the waiter infer it from a column written for another question. [cd](services/chat-delivery.md)

- **A SEAM THAT CAN PROVE A FRAME IS UNDECRYPTABLE BY CONSTRUCTION MUST REFUSE IT, NOT FORWARD IT.** `status = 'active'` gated recipient resolution and nothing gated the SENDER, so a `pending` device - holding no leaf in the ratchet tree - had six messages fanned to five devices: thirty rows of ciphertext nobody in the group could ever open. The discriminator was in the row the server reads to address the recipients. The exception names itself: a Welcome and a Commit are the path OUT of `pending`, and refusing those makes the gate a deadlock. [cd](services/chat-delivery.md)

- **A LOG LINE NAMED AFTER ITS ENDPOINT COUNTS REQUESTS; ONLY ONE NAMED AFTER ITS OUTCOME COUNTS EVENTS.** An idempotent write is CALLED on paths where there is nothing to do - and a dismissal is per USER while the call that lifts it is per DEVICE, so one re-add on a two-device account is two requests and at most one lift. Print what changed (`lifted=`, `recorded=`), or the line claims an event on every no-op and a reader counting them counts traffic. [cd](services/chat-delivery.md)

- **A SELF-EXCLUSION WRITTEN AT USER GRANULARITY EXCLUDES A DEVICE, AND THE DEVICE WAS THE HOLDER.** Anything addressed to a USER reaches every OTHER device of theirs and only them - MLS never hands a sender its own frame back - so "never ask ourselves" silently drops the one candidate that can be named with certainty: the device of ours that minted the thing. Before excluding a party, name the granularity the address actually has, and ask what a POPULATION of one member and two devices does to the walk. [chat](frontend/modules/chat.md)

- **"RETRYABLE" IS A CLAIM ABOUT SOMETHING ELSE HAPPENING, AND THAT SOMETHING MUST BE NAMED AND MADE TO HAPPEN.** A staged commit refused for `epoch_mismatch` rolls back cleanly and was documented as retryable - true only while the commit we missed reaches us through the fan-out, which is the concurrent-commit case it was written for. On a quiet conversation the refused commits ARE the only traffic, so nothing arrived, no rung of the recovery ladder ran, and the same commit was refused 191 times in a day. **A recovery ladder is only as reachable as its entrances**: both rungs hung off the READ side (a frame that will not decrypt), and the write side learned the identical fact - the server answers a refusal with its own `activeEpoch` - and reached nothing. Before calling a failure retryable, name the event that makes the retry different, and check the path where that event never comes. [mls](protocols/mls-recovery-ladder.md)

- **A REFUSAL NO RETRY CAN LIFT MUST NOT BE LOGGED AS A DEFERRAL, AND THE ACTOR WHO CAN LIFT IT MUST BE TOLD.** The per-user device cap answers `400` forever - the account has to lose a device first - and the client called it "welcome_request deferred to next connection" on every reconnection, so a full account got a device with a session, no KeyPackage, `reason=no_key_package` in every group, and no healing. Carry terminal-vs-retryable as a TYPE from the seam that reads the status (`DEVICE_LIMIT_REACHED` -> `DeviceLimitReachedError`), and surface it, since only the user can delete a device. [cd](services/chat-delivery.md)

- **A GUARD THAT REFUSES BEFORE THE ENTRY LOG LEAVES NO TRACE OF THE REFUSAL.** The cap check fired above `[REGISTER_DEVICE] START`, so a refused registration was invisible on the server AND misdescribed on the client - two silences that together cost a night. A refusal logs its own line, carrying the count it read (`spent=15/15`). [cd](services/chat-delivery.md)

- **A CAPABILITY REMOVED IS URGENT IN A WAY A CAPABILITY GRANTED IS NOT** - a promotion arriving late is an annoyance, a demotion arriving late leaves somebody clicking controls the server now refuses. Push the change to the subject, carrying what the role GRANTS, not its name. [backlog](backlog.md)

- **AN ENTITLEMENT AND ITS ROUTING ARE ONE ACT, and a save that computes who it DROPS owes the same for who it ADDS.** `updateChannelAccess` wrote the access row and cut off the people it removed, and told the people it added nothing - so being let into a private salon was a database row until the recipient's next full page load, because the one event that both puts a salon on screen AND enters its distribution group was never published. When a method's two directions are not symmetric, the missing one is the defect, not the style. And the audience is not always a diff: **`allowedUsers` is evidence about who could SEE a salon and never about who is on its group** - on a flip to private the group was minted by that same request and holds only the flipper's leaf, so diffing rosters there answers a question nobody asked (COMM-23: one delivery row and epoch 0, against two rows and epoch 1 on the create path). The mirror flip has no MLS consequence and the same screen consequence, since `channel.updated` maps over the rows a client already holds and creates none. [chat](frontend/modules/chat.md)

- **A TREE THAT MOVED IN MEMORY ONLY IS A TREE THE NEXT LOAD WALKS BACK INTO - and the outcome worth persisting is the FAILING one.** The re-join path forgot a stale distribution group and joined again, and neither half was written to disk: a forget followed by a failed join is the ONE state where memory and disk disagree about a belief that is WRONG, and a reload resolves that disagreement in favour of the wrong side. Measured 2026-08-25 (WP-REGRANT-2), one second after `could not join the distribution group`: `[SYNC] WASM kept` for the group just forgotten, then silence from that salon for the rest of the session. Persisting it needs no retry and no clock - the device now holds nothing for the scope, which is the state every existing trigger already repairs. Condition the checkpoint on the tree having actually CHANGED, or a load whose salons are all joined pays an Argon2 pass each for nothing. [channel-encryption](protocols/channel-encryption.md)

- **CLASSIFY THE ANSWER BEFORE CONSULTING LOCAL STATE - the ORDER of the branches is the whole guarantee.** "A held group survives a failed read" is correct and was written first, so it caught every refusal of the distribution-group read including the one that settles the question: a 403 on a route authorized by membership of the scope. A revoked device therefore logged the sentence written for a lost packet (`keeping the one this device holds`), then reconciled its roster and asked for history on a salon it had just been refused. The discriminator was on `ChannelApiError` all along. **Only a refusal that says NOTHING about entitlement may fall back on what the device holds**, so every answer is separated above that branch, not beside it - and the answer that contradicts a DTO the caller already trusted is logged at a level that accuses, because it means two server routes disagree. Classifying is not repairing: dropping key material on one status is a destructive act owing its own evidence. [channel-encryption](protocols/channel-encryption.md)

- **A SHARED PREREQUISITE PUBLISHED BY ONE PARTICIPANT'S FIRE-AND-FORGET FOLLOW-UP IS A PREREQUISITE NOBODY OWNS.** The external-join base every future joiner of a scope depends on was minted by `void this.refreshGroupInfo(...)` from the single device whose commit had just been accepted, and NOTHING else ever minted another. Lose that one call - a closed tab, an offline moment, a refused refresh - and the group's epoch advances while the published base stays behind, permanently; the commit gate accepts equality and nothing else, so every device holding no local MLS state is refused on every attempt, and a distribution group has no peer-Welcome fallback by construction. That is a permanent lockout from a salon the user is entitled to, measured on production 2026-08-25 (COMM-8) as the same commit resubmitted for twenty minutes. **Ask of any state a group depends on: how many distinct events can write it, and is the one that must is also the one allowed to fail silently?** The repair is not a timer and not a sweep: every HOLDER's ordinary read of a scope it is already in compares the two epochs and republishes from the tree it holds, terminating on a proof the server hands over (`baseEpoch >= activeEpoch`), idempotent because the far side is monotonic, and sending nothing in the common case where the numbers agree. A device whose own tree is behind the group declines and says so rather than publishing an equally unusable base. And **serve both epochs from where they are already known together**: `published` answered "is there a base" and never "is that base usable", so the client learned the difference by building a tree and being refused. [channel-encryption](protocols/channel-encryption.md)

- **A COMMENT CITING A PRECEDENT IS NOT EVIDENCE THE PRECEDENT EXISTS.** The roster reconciliation persisted its own commit "for the same reason the join is" - and the join did not persist at all, in any of the three places it could have. That sentence is how the hole survived review: a reader checking whether joins were durable found a claim that they were. When a comment asserts that a sibling path does something, grep for it before believing it, and when writing one, name the function rather than the reason. [durable-rules](durable-rules.md)

- **A SKIP THAT PRINTS A COUNT CANNOT NAME ITS OWN CAUSE.** A transport-only frame is dropped for recipients Redis reports offline, which is correct - the rendezvous expires in 60 s. But `count=1` is written identically by "that device really was offline" and "the group named a device that is not the live one", which want opposite fixes; separating them on 2026-08-25 (COMM-18) meant reading Redis by hand against a group the run had already deleted, and it could not be settled. Print the ids the predicate was KEYED on, not how many there were. [cd](services/chat-delivery.md)

- **A GUARD'S PARAMETER MEANS WHAT THE GUARD ASKS, NOT WHAT THE CALLER HAS IN HAND.** `waitForMessageQueueIdle(caller, catchUpGroupId)` asks "which session am I INSIDE"; two call sites passed "the group I am working on", so a guard against a deadlock fired on every CONCURRENT overlap instead, accused it of being unresolvable, and skipped the very guarantee its caller had taken the barrier to buy. Enumerate who can actually be in the state a parameter claims - here, ONE function opens a session and its only caller closes it first, so the honest answer was `null` at both sites. [chat](frontend/modules/chat.md)

- **A WAIT REPORTED ONLY AFTER IT ENDS SAYS NOTHING ABOUT A WAIT THAT NEVER ENDS** - and that is the case the report exists for. State the wait BEFORE awaiting it, naming what is held and what to change; account for the duration afterwards. One line on the far side of an `await` accounts for latency perfectly and is silent on the hang. [chat](frontend/modules/chat.md)

- **A REMOVE COMMIT NAMES THE DEVICE IT EVICTS, SO EVICTION IS A FACT TO READ, NEVER A REFUSAL TO CATCH.** `is_group_active` answers it the instant the commit merges; holding a group's state and being a member of it are different questions, and `getLocalGroups().includes(id)` answers only the first. A device that learns it was removed by having something refused treats a correct group it is not in as a broken one it must repair - so it retries an encrypt that can never succeed, and asks the server to undo a moderation action. [graine](protocols/channel-encryption.md#the-asymmetry-has-a-third-half-coming-back---fixed-2026-08-21-wp-regrant-1)

[graine](protocols/channel-encryption.md#the-asymmetry-has-a-third-half-coming-back---fixed-2026-08-21-wp-regrant-1)

[mls](protocols/mls-protocol.md)

[mls](protocols/mls-protocol.md)

**Markers, and what discharges them**

- **A durable marker must carry the EVIDENCE that justified it**, or nothing can revisit the diagnosis; one written without evidence is legacy - drop it, do not replay it. [hr](protocols/history-reconciliation.md)
- **A marker is discharged by anything that FALSIFIES ITS OWN EVIDENCE, not only by the answer it waited for** - so the discharges differ per reason, and a guard implemented as SILENCE makes a fixed point no convergence argument covers. [hr](protocols/history-reconciliation.md)
- **A device that has not noticed its own gap will VOUCH for its store**, promoting a silent upstream failure into a trusted witness for everyone else's repair. [hr](protocols/history-reconciliation.md)
- **A responder is elected at RANDOM among the online devices**, so any check on a repair must record WHICH device answered - the greener verdict is the one that says less. [testing-methodology](testing-methodology.md)

- **A device good enough to be MESSAGED must be at least as valid as one good enough to be INVITED** - the invitation path checks the key package, the fan-out does not. [cd](services/chat-delivery.md)
- **When a resource keeps refilling, deleting it is not the fix - REVOKE whatever keeps naming it as a destination.** A DELETE leaves the routing memberships standing and the count starts over. [cd](services/chat-delivery.md)
- **When two paths both END the same thing, "what it owns" is ONE exported list or it is neither** - and the owned rows drop in the SAME transaction as their parent. [cd](services/chat-delivery.md)
- **THE LIST IS OWED BY EVERY ROUTE THAT ENDS THE THING, NOT BY THE JOBS THAT COLLECT ONE** - the rule above shipped, and for three days its only callers were the reaper and the orphan sweep while all THREE delete routes still carried a hand-written subset, one of them empty. The doc said "both ways a group ends call it" and named the two collectors, which is a claim about the wrong pair. When a shared list lands, enumerate its call sites against the acts that END the thing. [cd](services/chat-delivery.md#what-a-group-owns-and-the-one-list-that-says-so)
- **A ROW KEPT ON PURPOSE HIDES ITS OWN LEAK, PERMANENTLY** - the orphan sweep finds groups with NO row, so it is structurally blind to whatever a SOFT-delete forgot: the tombstone survives by design, so nothing collects the residue before the 90-day reaper. [cd](services/chat-delivery.md#what-a-group-owns-and-the-one-list-that-says-so)
- **A ROW IS NOT A DESTINATION: PRESENCE AND DELIVERABILITY ARE TWO QUESTIONS** - `purgeOrphanGroups` answered "does the row exist" while its own doc named the other one, "still present (deliverable)", and the two differ by exactly the tombstones. Handing a frame to a client that can neither decrypt nor ACK it starts a loop nothing terminates: it asks for keys, is told nothing, keeps the frame, meets it again next connection. The one-word conflation was in the DOC first. And return the two sets NAMED, because the causes accuse different code - absent is this call's to repair, tombstoned is a delete route's. [cd](services/chat-delivery.md#a-row-in-dm_groups-is-not-a-place-a-frame-can-go)
- **A SHARED "WHAT IT OWNS" LIST IS NOT THE SAME LIST FOR A SOFT DELETE AND A HARD ONE** - one member of it, `dm_user_dismissed_groups`, is a fact about a PERSON that is BUILT to outlive the group row (text, not a relation, and its entity says so twice). Unifying three soft routes onto the list put all three on the wrong side of that, and a by-hand repair took 25 rows before anybody noticed. Before adding a table to such a list, ask WHOSE fact the row is and WHO still reads it after the parent dies - and let the caller declare which kind of death it is. [cd](services/chat-delivery.md#what-a-group-owns-and-the-one-list-that-says-so)
- **A SECOND COLLECTOR FOR RESIDUE THE FIRST ONE SHOULD HAVE TAKEN HIDES THE FIRST ONE'S ABSENCE** - so the fetch path DROPS an undeliverable frame and NAMES its group at WARN, and sweeps nothing: the rows exist because a delete route leaked, and the fix belongs there. [cd](services/chat-delivery.md#a-row-in-dm_groups-is-not-a-place-a-frame-can-go)
- **A sweep that looks for orphans where the reaper already deleted finds none, and reads as PROOF that there are none.** Read a cleanup's predicate against what runs BEFORE it. [cd](services/chat-delivery.md)

**Classifying a decrypt failure**

- **ONE SERVER ROW, ONE DECRYPTION - AND THE ROW'S IDENTITY IS THE SERVER'S QUEUE ID.** A frame arrives by two independent channels, the live socket and the `/pending` pull, and nothing about either makes them one event: COMM-4 measured `qId=d4ecf0fe` absorbed off the socket and handed back by the pull a moment later, the second decrypt spending a ratchet secret the first had consumed. A single-use secret makes a duplicated DELIVERY indistinguishable from a corrupt MESSAGE, so the client declares a perfectly good frame unreadable for good and the heal makes the loss look handled. Dedupe at the ONE seam both channels pass through (`enqueueMessage`), keyed on that id, and never by widening a classifier - the raw failure must stay unexplained if it ever arrives by another route. `queued` and `done` are different answers to a repeat (mid-flight vs settled-so-ack-it-again), a delivery the drain deliberately left UNacknowledged has to be FORGOTTEN or the reconnect refetch stops working, and a frame the server never persisted carries no id and is always admitted. [chat](frontend/modules/chat.md)
- **An error says what it says**: "this generation is consumed" is NOT "I already have this message". A layer that cannot make a distinction must not make it - the guard is `same_epoch_ratchet.rs`, not a comment, and a test asserting the swallow will happily protect the bug. [mls](protocols/mls-protocol.md)
- **EPOCH and GENERATION are different axes, and so are their repairs** - a verdict computed over one must never answer a question asked about the other. [mls-recovery-ladder](protocols/mls-recovery-ladder.md)
- A wrapper string carries BOTH markers (`GAP_QUEUED:<group>:<error>`), so the ORDER of a substring classifier is a decision. [mls](protocols/mls-protocol.md)
- **A shim that downgrades a log's severity by RE-READING ITS TEXT is a missing classification, announcing itself** - where the demotion is, the classification is not, and the platform doing the damage is the one with no demotion at all. [mls](protocols/mls-protocol.md#our-own-frame-was-classified-as-a-retryable-gap-2026-08-15)
- **Severity is the CLASSIFICATION's to report, not the bare fact that a call returned `Err`.** Only what nothing has explained keeps `error!`. [mls](protocols/mls-protocol.md)
- **A comment asserting where a line comes from is a CLAIM, and it is cheap to refute** - a bad measurement is worse than none, because it gets written down. [testing-methodology](testing-methodology.md)
- **CLASSIFY THE SITE, NEVER THE LINE.** A run finds spellings one at a time: three GRP passes came back `PASS-DIRTY` on three rows, three lines and two log sites saying the same thing in a wording the classifier had not met - and each fix landed MID-RUN, which is what actually disqualified the run (passes measured against different rule sets are not five passes of one check). When a line lands in `unexplained`, enumerate every log call under its tag in one pass, take a variable's values from its TYPE rather than writing `\S+`, MEASURE where each spelling already lands instead of assuming, pin them all in `classify-selftest.mjs`, and name in place the ones left deliberately ruleless. **And some line is UNPINNABLE, at which point the dirt is the correct price.** COMM-24's `served ... published=false base=none active=0` is the ordinary answer one second after a salon is created - and also, word for word, what BOTH callers of the concurrent-join race read. No text separates them, so pinning the shape to clean the row would delete the rig's only detector for the race. A row that stays `PASS-DIRTY` with its dirt named costs one cell; a classifier widened to green it costs the next incident. And check the LEVEL: `console.warn` has a bucket that never breaks `clean`, so a warn that names a defect is silent until a `SEVERE` rule claims it. [testing-methodology](testing-methodology.md)
- **A TEST ACCOUNT'S OTHER SESSIONS ARE PART OF THE CHECK WHETHER OR NOT THE RIG KNOWS THEM.** Every device of a group's creator is fanned into every group a check makes, so an undriven one that is slow to process its Welcome reaches the kick + re-add repair and dirties the row correctly. Enumerate who else is online before blaming the product - the pre-flight now prints it. [testing-methodology](testing-methodology.md#environment-traps-that-read-as-application-bugs)

## Outbound delivery -> [chat](frontend/modules/chat.md), [history-reconciliation](protocols/history-reconciliation.md), [chat-delivery](services/chat-delivery.md), [mobile](frontend/mobile.md)

- **A RECORD THAT EXISTS ONLY TO BE REMOVED MUST NOT BE ABLE TO REFUSE ITS OWN REPLACEMENT.** A
  `removed` conversation is a tombstone - deleted by a peer, an exclusion, or a local deletion the
  server has not answered - and it stays in the store until a MANUAL deletion, so it is present and
  matched like any other. Two independent de-duplication sites keyed on the peer alone: one declined
  to create the replacement (the user's 2026-08-23 report), and the login-time merge, which keeps
  the most RECENT record and deletes the others locally AND on the server, absorbed a conversation
  the user had just started and deleted its group for the other party too. **When two sites ask the
  same question, the question is a predicate with a name, not a condition each writes for itself** -
  they had diverged on nothing and were wrong together. And the anti-vacuity half matters as much as
  the fix: a guard that switched de-duplication off would satisfy every tombstone case while
  resurrecting the duplicate-DM defect the merge exists for. [chat](frontend/modules/chat.md)
- **BEING REACHABLE AND BEING ABLE TO ROUTE ARE TWO FACTS, AND ONE STRICTLY PRECEDES THE OTHER.**
  `externalJoin` publishes this device's leaf: from the instant it returns, every member may address
  the group and the delivery service routes to it. What makes an arriving frame usable is a
  conversation row, and that row was written by a DIFFERENT sweep over the SAME server list
  (`discoverMissingGroups`, fire-and-forget, its own cadence) - so the order between the two halves
  of one act was decided by whichever finished first. Measured 2026-09-06 (HEAL-REVOKE-4): the join
  won by five seconds, and the member's answer to this device's own history solicitation - sent in
  the same second as the join - was refused `absent-conversation` and left in the server queue, where
  nothing collected it until the next reconnect. Every layer reported success:
  `online=true ... realtime=1`. **Never let a device become addressable for something it is not yet
  ready to be addressed about**, and when one act is written by two sweeps, the order is not an
  implementation detail - it is the contract. The Welcome path had it right all along by doing both
  under one lock; the fix is to make the other path the same shape, not to add a trigger that
  repairs the gap afterwards. [history-reconciliation](protocols/history-reconciliation.md)
- **A BUFFER'S DISCHARGE MUST BE THE EVENT THAT MAKES ITS CONDITION FALSE, NOT A LARGER EVENT THAT
  USUALLY CONTAINS IT.** The same frame's reason, `absent-conversation`, was collected only by the
  boot restore - a one-shot that had already fired, and that cannot by construction produce a
  conversation the local store has never held. A global trigger for a per-group condition is a
  trigger that is wrong exactly when the condition is new. [chat](frontend/modules/chat.md)
- **MAKING ONE THING WAIT ON ANOTHER INHERITS ITS TERMINATION PROPERTIES, INCLUDING THE ONES
  NOBODY HAD TO THINK ABOUT.** `ackMessagesWithRetry` bounded how many times it gives up - four
  attempts - and bounded nothing about how long ONE attempt may take: its `fetch` carried no
  signal and no timeout. That was invisible for as long as every caller `void`ed it, because a
  promise nobody awaits may hang for ever at no cost. The moment a pull was ordered behind it, an
  open silent socket stopped being a hung request and became a mailbox that never drains again -
  and every ack chained behind it with it. **A RETRY COUNT IS NOT A DEADLINE**: a loop of four
  attempts can be four unbounded waits, and the loop cannot tell, because it never gets control
  back. So when you add a barrier, re-read what is now BEHIND it and ask of each thing whether it
  is guaranteed to conclude - not whether it usually does. Found by asking that question, not by
  an incident. [backlog](backlog.md)
- **FIRE-AND-FORGET IS A LATENCY DECISION, NOT AN ORDERING ONE, AND THE TWO ARE SEPARABLE.** A
  request that must not block its caller can still ANNOUNCE itself, and the one path that must not
  overtake it can then wait. Every ack in `BaseMlsService` was correctly `void`ed - a drain must not
  wait on an HTTP round trip - and that was read as licence to let a pull start beside one.
  `onDrainEnd` acknowledges the rows it drained and, in the same tick, `refetchFramesLeftBehind`
  pulls; the server has not recorded the ack, so it returns those rows and the device meets its own
  frames again. **Ask of every `void`ed call what must not overtake it. If the answer is not
  "nothing", it owes a promise somebody awaits** - and the fix is that promise, never an await at
  the call site, which would trade the defect for the stall the `void` existed to prevent. Second
  time this exact shape has been paid for: WP-DUPDELIVERY-1 was the mirror image, a pull racing the
  archive replay. [backlog](backlog.md)
- **A DEFECT'S CAUSE IS OFTEN IN THE ROW THAT DID *NOT* REPRODUCE IT.** Four campaign rows carried
  `delivery ... arrived twice` and all four were an empty store draining a backlog, which suggested
  the store. HEAL-NEW-1 has an equally empty store and stayed clean - because nothing was online to
  deliver anything, so there was no drain, no ack and no re-fetch. **The negative case is what
  turned a correlation into a mechanism**, and it was already in the ledger. Before theorising from
  the rows that failed, find the nearest row that should have failed and did not.

- **A HANDSHAKE WHOSE RESPONDER WAITS A FIXED DURATION AND WHOSE ASKER ANSWERS AFTER UNBOUNDED WORK IS A RACE, AND IT IS LOST BY WHICHEVER DEVICE HAS JUST WOKEN UP.** The history reconciliation's second leg asks *describe yourself* and waits `DIGEST_TTL_MS` = 60 s; the asker answers only `answerAfterMailboxDrained`, deliberately, because a digest computed mid-queue describes a store still being completed. Both halves are right on their own. **Measured 2026-09-05: a device that had just rejoined took 67 s to drain twenty external joins and sent its digest seven seconds after the responder logged `no digest came`.** Nothing retried, and the reason is the SECOND half of the rule. The trigger that would have retried did fire - `holds 4 frame(s) it can never read` six seconds after the join - and it was swallowed by a 30 s coalescing window whose written justification is *"the next connection re-asks unconditionally either way"*. **A session that stays up has no next connection**, and the trigger's evidence is spent, so the deferral is permanent. The order pair of HEAL-REVOKE-7 isolates it to one number: the same runner, one variable, and the run whose first ask nobody could answer is the run that ends up COMPLETE, because its retry landed 42 s later, outside the window. **Two rules follow.** A deadline is not a termination proof - raising the 60 s buys the next slower boot nothing - and a leg that needs no remembered state to answer must not require a live waiter to answer it. And **coalescing is a promise that the in-flight ask covers the trigger it swallows**: where that cannot be shown, the swallowed trigger is REMEMBERED and re-asked when the window closes, never dropped against a reconnection that may never come. It cost two rows, HEAL-REVOKE-5 and HEAL-repair, read as two problems until the trail was captured. **And a
SECOND cause with the same symptom was found by the re-run**: a server that elects a RANDOM
responder so that retries can rotate past a frozen peer is written against a client that retries,
and this one did not - so a returning device asked a sleeping phone once and stopped, while a
reference device that happened to ask twice drew a live member and was whole. **When a component's
comment names the behaviour it depends on from its counterpart, that is an assertion nobody is
checking.** The escalation that closes it is gated on LOCAL EVIDENCE - a frame this device holds and
cannot read - because silence from a responder means both *we agree* and *nobody answered*, and
those cannot be told apart from an absence. [backlog](backlog.md)

**Two mechanisms, one user-visible outcome, and nobody owning the gap**

- **A PATH THAT STAYS QUIET BECAUSE ANOTHER PATH WILL SPEAK MUST NAME THE CONDITION UNDER WHICH THAT
  OTHER PATH RUNS - and something must assert the two conditions cover everything.** `notifyInbound`
  returned immediately on native mobile, with a comment that is a complete argument and a wrong
  premise: *"the background push handler posts its own, so the user would get two"*. The push
  handler runs only when the server sends a push, and the server pushes only a message the device
  has NOT acknowledged after 10 s - so for a backgrounded app, which keeps its WebSocket, receives
  the message and ACKs it, there is no push and the handler never runs. **Neither half spoke, and
  the user was never told about a message sitting in their own app.** Measured on device 2026-09-05
  by correlating all three sources on one message: `[SEND] PUBLISHED recipient=...:tauri-...` with no
  `[PUSH_DEFERRED]` after it, an empty shade, and `A1 holds the message: 1`. The two conditions were
  complementary in somebody's head and overlapping nowhere in the code. Where a partition like this
  is load-bearing, the cheap version is a log line on each side saying which case it took; the honest
  version is a test that drives both. [chat](frontend/modules/chat.md), `mob`

- **A CAUSE IS NOT ESTABLISHED UNTIL THE THING THAT WOULD HAVE PRODUCED THE SYMPTOM IS SHOWN TO HAVE
  RUN AT ALL.** The same defect was filed for a day against a `SecretReuseError` that logcat shows on
  every message - loud, at `E/`, naming the right group and the right epoch, and belonging to a
  SILENT frame travelling beside the message, which raises no notification whatever it decrypts to.
  The evidence was never wrong; it was never connected. One field settled it, and it was in the line
  the whole time: the push's `queuedMessageId` is the id of the frame it carries, and it was not the
  message's. **A loud error next to a symptom is a coincidence until something ties them together** -
  and the tie has to be an identifier, not a plausible story. Corollary, paid for twice here: the
  first thing to ask of a missing notification is not why the decrypt failed but whether anything was
  ever sent. `cd`, `mob`

- **A ROW'S VERDICT MEANS WHAT THAT ROW ASSERTED, AND "IT PASSES" IS NOT A MECHANISM.** The same
  investigation cited LIFE-3 - *"which KILLS the app, passes, so a killed app's push must fire"* -
  in a backlog entry, a code comment, a CHANGELOG entry and a pull request, and it was wrong in all
  four. LIFE-3 **force-stops**, and `life.mjs` says what that means: a force-stopped package sits in
  Android's STOPPED state and the framework cancels every FCM broadcast to it, so the row records
  `notification: {expected: false}` and passes because nothing was owed. The claim itself was true
  and the evidence for it was a DIFFERENT row - LIFE-8, `am kill`, a decrypted push in 4.7 s.
  **Before a green row is used as evidence for a mechanism, read what it asserts**: a verdict is an
  answer to one question, and the phase index is not that question. It was caught by re-running the
  row for an unrelated regression check, which is the cheapest way it could have been found and was
  luck rather than method.

- **`document.visibilityState` AND `document.hasFocus()` ARE BOTH PERMANENTLY TRUE IN A BACKGROUNDED
  ANDROID TAURI WEBVIEW, so every "is the user looking at this" decision is wrong on a phone, in the
  direction that says yes.** Measured on device 2026-09-05 (Mi 9T, Android 16): backgrounded with
  HOME, the page reports `{visibilityState: "visible", hidden: false, hasFocus: true}` - byte for
  byte its foreground answer - while its JS keeps running (a 1.5 s timer fired in 1507 ms). It is
  NOT a missing lifecycle call: `WryActivity.onPause` already calls `mWebView.onPause()`, and
  `WebView.onPause()` does not drive the Page Visibility API. **Two things depended on it and both
  were wrong**: a backgrounded phone raised no notification for a message no push would ever carry
  (see the rule above), and it sent a READ RECEIPT for a message nobody had seen - `MainChatPage`
  gates the watermark on `isWindowFocused && isTabVisible`, and on Android both are constants.
  `MainActivity.isInForeground` is the one honest statement of the fact in the process; the activity
  pushes it into the page as `window.__canariForeground` plus a `canari:foreground` event, and
  `isAppInForeground()` reads it - returning `true` wherever nothing states it, so web and desktop
  keep deciding from their own working API. **The first fix for the notification was written against
  the document and was INERT; only the device said so.** Any new visibility check on a path that
  runs on mobile has to ask this instead, and the remaining call sites are a filed sweep.
  [mobile](frontend/mobile.md), `frontend/src/lib/utils/appForeground.ts`

**What the sender keeps, and what the queue will send**

- **TWO FACTS THAT MUST BOTH BE TRUE ARE ONE WRITE.** The optimistic echo and the outbox entry that delivers it were persisted by two consecutive awaits, and a document torn down between them left a `pending` message on disk that no queue knew about - never sent, never retried, never reported, and visible to its author for ever. TAB-5 reloads 15 ms after the click and reproduces it. `saveMessageWithOutboxEntry` puts both rows in ONE IndexedDB transaction; both payloads are encrypted BEFORE it opens, because an `await` inside a transaction ends it and would restore the very gap being closed. [chat](frontend/modules/chat.md)
- **WHERE ATOMICITY IS UNAVAILABLE, CHOOSE WHICH HALF SURVIVES THE TEAR - never leave the order to chance.** SQLite through `tauri-plugin-sql` pools connections, so a statement is the largest unit of atomicity there is. The entry is therefore written FIRST and the message second: entry without message still delivers to the peer and costs the sender an echo, while message without entry is silent loss for everyone. The two are not symmetric, so the order is a decision and is written down as one. [chat](frontend/modules/chat.md)
- **A FACT CHECKED OVER A ROUND TRIP IS A FACT THAT CAN GO STALE INSIDE IT - only the writer can make the check and the write atomic.** The outbox asks the server whether a group is deleted before it sends, and the server answered `found=true` one log line before a `[DELETE_GROUP]` landed between that send's recipient resolution and its enqueue: two rows written into a queue the delete had just swept, for a group that no longer existed, undeliverable until the 90-day reaper and re-dropped on every device's every connection. Moving the check closer to the send would only shorten the window. `enqueueForLiveGroup` reads the group row `FOR SHARE` in the same transaction that writes the rows, which orders the two in BOTH directions - the delete blocks behind the send and sweeps its rows, or the send blocks behind the delete and refuses. **Delete the overlap, never reconcile it**: the drop filter in `fetchMessages` was the witness, and a witness is not a fix. [chat-delivery](services/chat-delivery.md)
- **EVERY BRANCH THAT ENDS A DECISION MUST RECORD IT, INCLUDING THE ONE THAT LOSES.** The Web Locks election recorded `leader` on the winning path and nothing on the losing one, so a follower tab stayed `undecided` for its whole life and every write it queued was handed to nobody. It was invisible because `getIsTabLeader()` reads `undecided` as `false`, which is right for every caller except the one asking whether the answer EXISTS yet. **A predicate is only evidence for the question it was written to answer** - and the tests missed it for the same reason the code did: every assertion in the file read the predicate that cannot see the third state. Assert on the state, not on the shortcut. [chat](frontend/modules/chat.md)

**The push payload, and what sizes it**

- **A LIMIT IS ONLY EVIDENCE FOR THE QUANTITY IT WAS MEASURED OVER, and a payload is not its largest field.** The FCM guard capped the ciphertext at 3 500 B under a comment naming the 4 KB PAYLOAD budget - nine other fields, key names included, rode with it uncounted. A budget is computed from the fields that must be there, never chosen ahead of them. [chat-delivery](services/chat-delivery.md#transport--single-gateway-fcm)
- **SENDING BOTH HALVES SO EITHER PLATFORM CAN READ ONE IS SENDING THE MESSAGE TWICE** - the transport sizes the message, not the half the device will read. `data` 3 789 B + `apns` 4 005 B = 7 794 B against a 4 096 B limit, each half fitting alone. The platform is KNOWN at the call site, so carry the discriminator there rather than paying for both. [chat-delivery](services/chat-delivery.md#transport--single-gateway-fcm)
- **A REFUSAL THAT NAMES NO QUANTITY IS NOT A MEASUREMENT** - "Message is too large" ten times over says nothing about which field grew. The failure branch holds the payload: report the bytes and the largest field there, or the number is found by hand a day late. [chat-delivery](services/chat-delivery.md#transport--single-gateway-fcm)

**Converging on one answer**

- **AN APPLICATION FRAME AND A LOCAL EPOCH ADVANCE MUST NOT STRADDLE, AND TWO PAST EPOCHS OF TOLERANCE IS WHAT HIDES IT.** A send is encrypt-then-POST with a suspension between; a commit is stage-accept-merge. Nothing ordered the two, so a frame encrypted at epoch N could reach the wire after this device's own commit had moved everyone to N+1 - a past-epoch frame for every recipient. OpenMLS retains two past epochs, so ONE straddle is survived and nothing is ever reported; two commits in quick succession make the frame undecryptable for good, with the sender considering it delivered. Measured on prod 2026-09-02: seven frames across commits 128 and 129, the first 36 ms after the commit, four lost. **Delete the overlap, never reconcile it** - re-encrypting a frame found stale is a race that heals cleanly, which is still a defect. The barrier ([epochSendBarrier](../../frontend/src/lib/utils/chat/epochSendBarrier.ts)) is raised only under the MLS mutex, and that is the whole deadlock argument: a send that observes it provably does not hold the mutex the advance needs. [chat](frontend/modules/chat.md)

- **APPLYING A MUTATION ON ARRIVAL IS NOT A CONVERGENCE RULE - it is a different answer per device.** `edit_message` was applied unconditionally by all three paths that apply one, so two devices of one account editing one message each applied their own and then took the other's, ending on OPPOSITE bodies, permanently, with no error. Every mutation that two devices can issue at once needs a total order they both compute: `editSupersedes` and `pinStore.supersedes` are that, and a tie needs a rule for the same reason the ordering does. [chat](frontend/modules/chat.md)
- **CONVERGENCE DOES NOT NEED THE RIGHT WINNER, ONLY THE SAME WINNER** - which is what makes a sender-stamped wall clock sufficient here where the repo otherwise distrusts clocks. Two skewed clocks change WHICH edit survives; they cannot make two devices disagree, because each decides from the same pair of values. State that trade-off on the function, so the next reader does not "fix" it into arrival order. [chat](frontend/modules/chat.md)
- **A DELETE IS ABSORBING, AND AN INVARIANT HELD IN ONE OF THREE PLACES IS NOT HELD.** `edit_message` never checked `isDeleted`, and the tombstone lives in `content` - so an edit landing on a deleted row restored the text the user deleted, italic and faded. The rule "a tombstone wins whatever the order" was already in the archive's post-save pass and asserted by the campaign for merges; the live path and the replay had never had it. When a mutation seam has several appliers, enumerate them ALL and check the invariant in each. [chat](frontend/modules/chat.md)
- **ONE ACT, ONE INSTANT.** A local apply and its broadcast that each read the clock date the same act differently. Harmless while the value is only displayed, and not harmless the moment it decides a winner: a device that disagrees with its own broadcast can lose to itself. The caller takes the instant and passes it to both halves. [chat](frontend/modules/chat.md)

**The queue, and cancelling what is in it**

- Every step is best-effort, so **every swallowed branch logs**. [chat](frontend/modules/chat.md#outbox-outbound-delivery)
- **`void promise` IS A SWALLOWED BRANCH TOO, AND THE UI HAD ALREADY PROMISED IT WORKED.** Discarding a promise is ordinary and mostly harmless - there are 278 such call sites in the frontend and almost all are right. What makes one dangerous is not the `void`, it is what the interface has already told the user by the time the rejection arrives: `MainChatPage.handleSendChat` cleared the composer SYNCHRONOUSLY and let the send run on, over a `sendChatMessage` that awaits `enqueueOutboxMessage` with no `catch` of its own - so an aborted IndexedDB transaction left the box empty, a bubble stuck on `pending`, no error, and nothing in the log. The one failure a durable outbox cannot survive is the one it never hears about. So the test is not "is this awaited", it is **"has the user already been shown a success this promise could contradict"** - and a `void` on such a path owes a `catch` that says so on both surfaces. [chat](frontend/modules/chat.md#outbox-outbound-delivery)
- **THE SILENCE YOU KEEP IS THE ROUTINE ONE, and every abnormal return accuses** - the two rules meet here, and getting the split wrong costs either a defect nobody can name or a line every reader learns to skip. `drainPendingGroupExits` returned a bare `[]` for no-storage and for re-entrancy, and an empty array is what a trigger that NEVER FIRED returns too, so a reconnect that replayed nothing had four causes and no way to tell them apart; `owed.length === 0` stays silent because it runs on every reconnect of every session that owes nothing. [chat](frontend/modules/chat.md)
- **EVERY MESSAGE KIND LOGS ITS ARRIVAL, INCLUDING THE ONE THAT RENDERS NOTHING.** Text, media, reactions and calls each announced themselves; a SYSTEM event announced nothing, so a frame that decrypted and produced no visible change left no trace on any machine and could not be told from one that never arrived. A branch may still decline what it was sent - most system events are addressed - but the DISPATCH is a fact, and a fact nobody records is one the next reader has to reproduce on a live browser. [chat](frontend/modules/chat.md)
- **A `catch { /* noop */ }` around a PARSE turns malformed into absent.** An event whose payload did not parse was handled as an event with no data, which every addressed branch reads as "not for me" and answers by succeeding. [chat](frontend/modules/chat.md)
- **An operation on a queued object must CONSULT the queue, never queue a second one beside it.** [chat](frontend/modules/chat.md#outbox-outbound-delivery)
- **A branch the callee took is a fact the caller needs - return it as a TYPE.** [chat](frontend/modules/chat.md#outbox-outbound-delivery)
- **A cancellation is only as deterministic as the narrowest window it closes.** [chat](frontend/modules/chat.md#outbox-outbound-delivery)
- **A LOCAL PURGE IS NOT AN EXIT.** Destroying our copy of a group tells the server nothing, so a delete decided offline needs a DURABLE row saying the server has not been told - written before the call, cleared only by an ANSWER, replayed on `connectivity.onReconnect` plus one startup pass for an app killed offline. `exitGroupAndCleanup` had one `try/catch` over both halves and purged unconditionally, which read "404, already gone" and "no network at all" as the same event; discovery then handed the group back as a placeholder. And the discovery side has to consult what is owed, or the row is correct and the placeholder still appears. [chat](frontend/modules/chat.md#an-exit-is-owed-to-the-server-and-the-local-purge-is-not-what-pays-it-del-10)
- **TWO CALL SITES READING ONE FAILURE NEED ONE CLASSIFIER, NAMED, RETURNING A TYPE.** A drain and the composable that fills it must agree on what a 403 means, and if they each test the status in-line they will eventually agree on nothing - which is the same defect with its halves swapped. And the default matters: everything-not-a-status is NOT "unreachable", because a programming error thrown inside the call would then keep a row for ever while blaming the link. [chat](frontend/modules/chat.md#an-exit-is-owed-to-the-server-and-the-local-purge-is-not-what-pays-it-del-10)
- **Bound the work that consumes an IRREVERSIBLE resource, not the work that costs time.** [chat](frontend/modules/chat.md)
- **The record of what is still owed is only as durable as its last write.** [mob](frontend/mobile.md)
- **The native mirror is READ as well as written**, so a wholesale rewrite needs an adoption pass. [mob](frontend/mobile.md)
- **A per-item API makes the per-item cost invisible**; across an FFI boundary the batch belongs on the SHARED side. [mob](frontend/mobile.md)

- **Terminate a paged pull on an EMPTY page, never on a short one.** [cd](services/chat-delivery.md)

**Lifetimes, and state that goes stale under you**

- **A HANDLER ON `svelte:window` IS BUBBLE-PHASE, SO ANYTHING THAT STOPS PROPAGATION BELOW IT IS A SILENT DELETE.** `Modal.svelte` stopped `keydown` on its panel - a correct mirror of the `click` stop that keeps a click inside the panel off the dismissing backdrop - and thereby made its own `svelte:window` Escape handler dead code in all twenty-two consumers, for two years, with the prop docstring still promising Escape worked. `focusTrap` is what closes it: it moves focus INSIDE the panel on mount, so no keystroke ever originates anywhere else. **A key is handled where it lands, not where it would have arrived**, and `click` and `keydown` do not want the same treatment just because they are on the same element. Measured by dispatching in both phases: it reached `window` on capture and never on bubble ([story](../../CHANGELOG.md)).

- **`if (!res.ok)` IS HALF OF A FETCH'S FAILURE SURFACE, AND THE OTHER HALF CARRIES A MESSAGE NOBODY MAY BE SHOWN.** A server that answers badly and a server that cannot be reached arrive by different routes - one as a `Response`, one as a rejection - and the three calls behind the encryption gate handled only the first, each with a proper Paraglide sentence. The rejection walked past into the outer catch, whose `msg` becomes the text in the modal, so a person unlocking their messages with no network read `Failed to fetch`: the browser's own words, in English, on a French screen, sounding exactly like "your PIN is wrong". **Wrap the call, not the branch** - and throw a TYPE, never the sentence: the first draft threw a bare `Error` carrying the translated text and destroyed the one fact worth keeping, so the layer above could see what the user would read and nothing about why. **AND THE SAME CATCH IS WHERE THE LOG LEVEL GOES WRONG**: one funnel handled every login failure with `console.error('[INIT] Login failed')`, so a mistyped PIN - the most ordinary outcome that screen has - produced the line a WASM build that would not load produces, and the discriminator sat unread one line below it. Split by whether the application is at fault (`isExpectedLoginOutcome`), name the code IN the line, and pin the union with an exhaustive test so the next code added cannot arrive undecided. Both halves were found by campaign rows reading what the product SAID, not only what it did. [story](../../CHANGELOG.md)

- **A BLOCKING GATE IS ONLY AS SHUT AS ITS LEAST-KNOWN DISMISSAL PATH - AND ON A PHONE THAT PATH IS THE BACK GESTURE, WHICH COMES THROUGH NONE OF THE THREE A `dismissible` FLAG WAS WATCHING.** `Modal.svelte` disabled the backdrop, Escape and the header cross, and went on pushing a history entry for every open modal - so `onPopState` called `onClose` on exactly the dialogs that had refused every other way of closing. The three gates survived only because each happens to pass `onClose={() => {}}`, which is a property of their call sites and not of the component, and they still paid for it: an entry nothing will ever pop eats one back press in silence. **Enumerate the paths INTO a decision before believing a flag governs it**, and gate the registration at the same place as the handlers. **The other half is that a gate must carry its own way out**: the PIN modal became undismissable and would have been a wall rather than a loop, because its only exits were a destructive reset and an account-deletion link, both behind a disclosure. The exit is on screen from the start, is the app's ORDINARY sign-out so it destroys nothing, and stays pressable while the operation the gate is waiting on is still in flight - a hung unlock is one of the states it exists for. [story](../../CHANGELOG.md)

- **AN `{#if}` IS A VISUAL GUARD, NEVER A TEMPORAL ONE: a child's prop expressions are re-read during TEARDOWN, after the `$derived` they guarded has gone `null`.** So `{#if v}<Child p={v.x} />{/if}` throws on unmount. Every nullable `$derived` passed as a prop takes `?.` and a default, whatever encloses it. It surfaced only on Android WebView - slower, more aggressive GC - which is what a race "impossible on the machine it was written on" looks like. [arch](frontend/architecture.md#a-prop-expression-is-re-evaluated-during-teardown-so-an-if-does-not-protect-it)
- **AN UNCAUGHT ERROR IN THE REACTIVE GRAPH IS PERMANENT UNTIL A RELOAD**, so a `svelte:boundary` is placed by the BLAST RADIUS of a failure and never by how important the component looks: a global service gets a logging `onerror`, a page gets a `failed` snippet with a reset, and a light component inside a page gets nothing at all - one more boundary only hides the one that matters. [arch](frontend/architecture.md#an-uncaught-error-in-the-reactive-graph-is-permanent-until-a-reload-so-boundaries-are-placed-by-blast-radius)
- **A STYLE IS NOT A STATEMENT, AND NEITHER IS A TRANSLATED WORD - PUBLISH THE FACT.** Every hook on `ConversationTile` was added after a reader had nothing honest to read: `data-ready` because the only sign of a syncing conversation was the "Sync" badge, whose text is a Paraglide message, so counting it counts the translation and silently returns zero the day the string moves; `data-conversation-tile`'s value because a count cannot answer WHICH; and `data-selected` (2026-08-29) because the only sign a tile had received a click was its selected Tailwind classes, so a restyle and a frozen app read alike. **The failure is always in the safe-looking direction** - "nothing is syncing", "the list is dead" - which is exactly the answer that lets a check pass over a broken app, or fail a working one. A fact the component already holds costs one attribute to publish and nothing to render. [cross-client-campaign](cross-client-campaign.md#16-heal---what-the-rows-are-and-what-they-cost)
- **A REFUSAL THAT ANSWERS THE QUESTION MAY BE REMEMBERED; A FAILURE TO ASK MAY NOT - AND A CACHE THAT KEEPS ONE BUCKET FOR BOTH PICKS THE WRONG DISPOSITION FOR ONE OF THEM.** `fetchUserProfile` evicted every rejection "so the next caller retries", and `resolveUserDisplayName` filed every rejection in a two-minute backoff with an accusing `warn`, a place in the failure RATE and a clear-on-reconnect. Both are right for a dead radio and wrong for a 404: the account is gone, no retry can make one, and the reconnect that refutes a network failure refutes nothing here. A mention of a deleted member therefore cost one request per chip mount, for ever, and rendered as a bare `@` because "not known yet" and "known to have none" left the resolver as the same `null`. **Classify at the THROW, as a type** (`isAbsentUserError`), and let the answer live for as long as it is true - the session, here. The resolver's own docblocks had stated the distinction twice while the code had no way to write it down, which is what a missing discriminator looks like from the inside. [chat](frontend/modules/chat.md)
- **A UI FLAG WITH NO COLUMN IS DERIVED ON EVERY READ PATH, OR IT IS LOST ON ALL BUT ONE.** `ChatMessage.isSystem` exists in memory only - neither `StoredMessage` nor the encrypted payload a history bundle is built from has room for it - so a reload and a peer's bundle each have to re-derive it from the sentinel sender, and a path that waited to be TOLD rendered a group notice as an ordinary bubble from an unresolvable author. One exported constant, one predicate, and a test that pins what actually crosses the wire. [chat](frontend/modules/chat.md)
- **A DESTRUCTIVE BRANCH'S REASON STRING IS PART OF THE MECHANISM, AND IT MAY NAME ONLY WHAT THE BRANCH READ.** `decideAbsentLocalGroupFate` destroys a group's local MLS tree under the reason *"conversation row held with no membership left"* and reduces no membership at all - its entire input is a `dm_groups` row and one local predicate. Nothing misbehaves while the code is right; the cost lands on the day it is not, because that sentence is the FIRST thing a reader reaches for when a group has been forgotten and nobody knows why, and it sent them to the wrong table. **Reasons are pinned by tests as STRINGS, because the string is the deliverable** - and one reason covering two server states is one state's answer being wrong. [chat](frontend/modules/chat.md#a-group-must-be-nameable-by-the-server-before-it-is-holdable-here-or-every-sweep-is-a-hazard)
- **A REPLAYED EVENT IS NOT A LIVE ONE, AND APPLYING IT IN ARRIVAL ORDER REPLAYS HISTORY AS IF IT WERE HAPPENING.** A reconciliation carries message frames and the read receipts that answer them, interleaved; both add paths incremented the unread badge per arrival, so a tile flashed read/unread for the whole replay. **Derive the displayed quantity from the durable fact - here this user's watermark, already persisted and already loaded - rather than mutating a running tally**, and the answer stops depending on arrival order. Two of the four writers already did; the fix was making the other two ask the same question, which also exposed that they disagreed about whether a system message counts. [history-reconciliation](protocols/history-reconciliation.md#the-unread-count-is-derived-from-the-watermark-on-every-path-that-writes-it)
- **PASSING AN ID AS ITS OWN FALLBACK UNDOES A RESOLVER THAT WAS CAREFUL NEVER TO RETURN ONE.** `getUserDisplayNameSync` documents that it never answers with an id; `splitTextWithMentions` handed it the id as the fallback, so every mention in the app rendered `@3f9a1c2b...` on a cold cache. **A fallback is the CALLER's decision and must be a value the caller would be content to keep**, because a parser that runs once per body cannot re-render when the real answer arrives - whatever it guessed is frozen. Where the answer is genuinely in hand at the moment of the action, seed it instead of guessing: the @-autocomplete row carries the name the user just clicked. [arch](frontend/architecture.md#a-synchronous-unknown-placeholder-is-indistinguishable-from-an-answer)
- **A LATCH NOBODY CAN READ IS LEARNED BY BEING REFUSED, AND SOME REFUSALS COST THE USER A SECRET.** `_refreshCredentialProvenDead` knew the session was over at the moment the encryption-PIN keypad mounted, but nothing exported it, so the prompt was shown, accepted a correct PIN, and closed onto the login gate a second later. Exporting an accessor was the whole fix; the discriminator has to reach the place the decision is MADE. **Then enumerate the decision sites before believing there is one** - the backlog said one, there were four, and the one that bypassed the shared gate was the re-prompt path nobody thinks of as a prompt. A site deliberately left ungated must say so in the code, or the next reader closes the gap and breaks it. [auth](frontend/modules/auth.md#a-prompt-is-declined-from-a-fact-never-from-a-refusal)
- **A BUSY FLAG RAISED AFTER THE AWAIT LEAVES THE AWAIT UNGUARDED - and the await is the only part slow enough to be seen.** Both login handlers awaited `refreshAppVersionCheck()` and only then set `isLoggingIn`, so the one call carrying a retry ladder (3 x 8 s plus backoff) ran with the button enabled, no spinner and no visible effect; a press on a degraded connection looked ignored, and pressing again was the only move the screen offered. Nothing was missing - `LoginForm` already had the `disabled` and the spinner - only the moment they were switched on. **Raise the flag on the first line of the handler and lower it on every path that returns early**, and be suspicious of any diagnosis blaming a hydration gap: under `ssr = false` the button is painted by the bundle that wires it, so that window does not exist. The same duplication that hid this hid its sibling - one handler awaited the async OIDC start and the other did not, leaving a `try`/`catch` that caught nothing and a form busy for ever. [auth](frontend/modules/auth.md#the-press-is-not-the-first-thing-that-happens-and-the-button-must-say-so)
- **A SHARED PIECE OF THE DOM HAS ONE WRITER, AND ITS VALUE IS RENDERED, NEVER EDITED.** `document.title` had two: `SeoHead` writes the route's, and `useNotifications` blinked an incoming call's bell by SAVING the current title, overwriting it and restoring the saved copy - so any third party's prefix was captured into that save and reinstated after the call, or erased by the restore. Save-and-restore is what makes a second writer unsafe, because the saved copy is a claim about a value somebody else owns. **Render the whole value from its inputs on every change** - here `(base, unread, bell)` - and the writer becomes idempotent, an accumulating prefix becomes impossible, and the base can be ADOPTED from the DOM by observation instead of every future title source having to know the reader exists. [chat](frontend/modules/chat.md#the-tab-is-an-unread-signal-and-it-needs-no-permission-2026-08-31)
- **A CONDITIONAL SIGNAL IS NOT A SIGNAL, AND ITS FIRST OCCURRENCE IS THE ONE IT SPENDS ON ITSELF.** The web's only out-of-page unread notice was a browser `Notification`, which returns early until a permission is granted - so the first message arriving while the tab was away bought the prompt rather than being delivered, and a user who declined once had nothing for ever after. An in-page badge does not fill that gap: it has to be looked at to be read. **When a mechanism can refuse, ask what the user is left with, and prefer the surface that asks nobody** - a title and a favicon cost a line each. This is not the fallback the rules forbid: no primary path is failing silently, it is a second unconditional surface for a signal that had exactly one conditional one. [chat](frontend/modules/chat.md#the-tab-is-an-unread-signal-and-it-needs-no-permission-2026-08-31)
- **A NORMALISATION APPLIED TO ONE SIDE OF A COMPARISON PASSES EVERY TEST WRITTEN IN ASCII.** Four matchers, the sidebar filter and the `<mark>` highlighter all folded CASE and not diacritics, so on a corpus that is French "reunion" could not find the same word with its accent - and nothing looked broken, because every unaccented query still found every unaccented word. **Fold BOTH sides, and test on the corpus the app actually carries**, not on the one a test file is easy to type in. The campaign row written to record the gap PASSED by asserting it, which is what a finding-shaped check does and why flipping the fix must flip the prediction and VOID the old runs. [chat](frontend/modules/chat.md#one-fold-behind-every-search-box-2026-08-31)
- **AN OFFSET FOUND IN A NORMALISED STRING MEANS NOTHING IN THE ORIGINAL, AND THE ERROR IS EXACTLY THE NUMBER OF CHARACTERS THE NORMALISATION DROPPED BEFORE IT.** A precomposed accented letter folds one to one; the same letter as base + combining mark folds two to one; one string can hold both. A highlighter that matched in folded space and sliced the original would drift left once per preceding accent - invisible in ASCII, wrong in every French message. **Carry a map back (`foldWithIndex`), or do not fold** - and walk CODE POINTS, so an emoji is one unit rather than two halves of a surrogate pair. [chat](frontend/modules/chat.md#why-the-highlighter-needs-a-map-and-not-a-length-assumption)
- **TWO COPIES OF A RULE CAN DISAGREE; SEVEN DO.** Seven call sites stripped accents by hand with THREE different character sets (`[U+0300-U+036F]`, `\p{Mn}`, `\p{Diacritic}`), so the same association name slugged differently depending on which screen created it, and two of the five slug builders left a trailing separator the trim existed to remove. The shared function takes the variation as a PARAMETER (`slugify(label, maxLength?)`, trimming after the cut) rather than leaving each caller to re-derive it. [chat](frontend/modules/chat.md#the-five-slugs-disagreed-and-one-of-them-was-reachable)
- **A cleanup that releases something acquired ASYNCHRONOUSLY must wait for the acquisition** - release inside the pending promise's `finally`, never beside it. [arch](frontend/architecture.md#a-cleanup-that-releases-something-acquired-asynchronously-must-wait-for-the-acquisition)
- **An index into an array you do not own is state that goes stale, and `slice` past the end is SILENT** - clamp on the READ side, never recompute on the write side (WP-EMPTYVIEW-1). [chat](frontend/modules/chat.md)
- **A promise that has REJECTED stays rejected**, so state a retry writes must be read from OUTSIDE the thing that failed. [posts](frontend/modules/posts.md#why-the-feed-reads-postsoverride-outside-the-await)
- **A synchronous "unknown" PLACEHOLDER is indistinguishable from an answer once stored** - return the absence, never the label. [arch](frontend/architecture.md#a-synchronous-unknown-placeholder-is-indistinguishable-from-an-answer)
- **A DEADLINE STAMPED BY ONE CLOCK MAY NOT BE COMPARED WITH ANOTHER** - and `Date.now()` inside a `$derived` is not reactive to time, so the comparison is made ONCE and stands for ever. Closing a channel poll wrote the server's now; the card read it against the browser's, lost by the 0.2-1.1 s the two clocks differ by, and rendered "0 min restante(s)" indefinitely while the server refused every vote into that poll with a 403 (COMM-15, prod, 2026-08-25). A sub-second skew is SUFFICIENT, which is why this is architecture and not NTP, and why a timer would only be wrong later. **Carry the decision, never its input**: the side that owns the clock says `closed`, and a component that renders the answer takes it as a PROP - only the caller knows whose clock its deadline came from. [social-service](services/social-service.md#channel-polls-and-who-decides-one-is-over)
- **A CONTROL MUST NOT DISPLAY A VALUE IT HAS NOT OBTAINED, and the server's default is not this side's answer to give.** The channel notification radiogroup seeded `all` and kept its previous value across reopens, so a member stored at `mentions` was SHOWN `all`; any caller that skips a click when the level already looks right then skipped it, and COMM-14 measured exactly that (`asked=all stored=mentions`) - a check unable to arm its own case. The same seed made a FAILED read indistinguishable from a real `all`, since `notifLevels` genuinely defaults to `all` when the channel is absent. Show nothing until the answer arrives, log the failure, and let the control's PRESENCE mean the question was answered. [chat](frontend/modules/chat.md)

**Effects, and the writes that feed them**

- **A BARE CALL INSIDE AN EFFECT INHERITS THE CALLEE'S READS AS DEPENDENCIES.** `$effect(() => { void q; doThing(); })` does not depend on `q` alone - it depends on everything `doThing` touches synchronously. Declare the triggers and `untrack` the call, or the effect's dependency list is whatever the callee happens to read today. [chat](frontend/modules/chat.md)
- **A FUNCTION THAT WRITES STATE ITS OWN CALLER READS IS A LOOP WITH THE TRIGGER ALREADY ATTACHED** - and a `set` mints a new object whether or not the contents changed, so "it only writes the same value back" does not stop it. Write on CHANGE, and never let a reader be the writer of what re-invokes it. Channel search was both at once: 4956 requests for one query, no result, no error. [chat](frontend/modules/chat.md)
- **A FILTER MUST COMPARE WHAT THE ROW DISPLAYS, NOT WHAT THE ROW IS KEYED BY.** A DM's `name` is the persisted `userId::peerId`; the label is resolved separately. Resolve once and let the filter and the render read the same value, or typing the visible name hides the row. [chat](frontend/modules/chat.md)

**Strings, and who is allowed to write them**

- **Nothing types a string as user-visible, so no compiler enforces Paraglide.** Default to it for ANY new user-visible string on the FIRST draft; a file's existing raw literals are not a precedent to extend. [arch](frontend/architecture.md#i18n-paraglide)
- **No user-facing string may name a sensor** - "empreinte ou Face ID" is wrong on every device, half the time. [auth](frontend/modules/auth.md)
- **A language setting belongs to the APP, not to the phone - and the RECEIVER is what picks it.** Paraglide covers the bundle and nothing else, so each native surface needs its own table AND its own resolver. [mob](frontend/mobile.md#the-language-a-notification-speaks)
- **The layer that cannot know the reader's language must not write the SENTENCE** - send a key from a closed set plus only what is untranslatable; a `locale` column is the wrong repair. [mob](frontend/mobile.md#the-language-a-notification-speaks)
- **A seam no build checks needs a test that reads BOTH sides** - `nativeStrings.test.ts`, mutation-checked by deleting one string. [mob](frontend/mobile.md)
- **A dev-facing sentence is a decision to report NOTHING, and it expires the day a surface appears** - giving a refusal a surface is what makes its string user-visible, so both land in the SAME change. Classify at the throw, switch exhaustively, keep `detail` untranslated and off screen. [backup](frontend/backup.md)
- **A DEV-FACING STRING IN FRENCH IS A CLASSIFIER MISS WAITING FOR ITS LINE.** The mirror of the Paraglide rule, failing the other way round: a sentence written for a developer is read by a TOOL as well, and every rule, self-test and eye downstream is English. `decideAbsentGroupFate` returned four French `reason:` strings, each of which reaches a log line - so the designed "this row is already removed" path had no classifier rule that could name it, and READ-10 came back `PASS-DIRTY` on its own success. Translate at the source; do not teach the classifier the wrong language. [chat](frontend/modules/chat.md)
- **A rule that says "remember to run X first" is a MISSING DEPENDENCY, not a rule** - when two scripts need the same precondition and only one declares it, the other has a bug. [arch](frontend/architecture.md#linting-and-checks)

**Widgets**

- **A one-way colour is a dark-mode bug waiting to happen** - use the `app.css` tokens, and do not "fix" the 31 the sweep left deliberately. [arch](frontend/architecture.md#finding-one-way-colours)
- **Portalling a dropdown breaks its accessible RELATIONSHIP as well as its positioning, and nothing warns** - `aria-controls`, and a DISCLOSURE role, never `role="menu"`. [arch](frontend/architecture.md#an-anchored-dropdown-must-be-portalled-never-absolutely-positioned)
- **Two copies of a dialog do not stay identical, they stay PLAUSIBLE** - one shell owns chrome, focus and Escape, and deliberately NOT the content area (WP-VIEWER-1). [posts](frontend/modules/posts.md#the-two-viewers-share-one-shell-and-two-zoom-models-wp-viewer-1-2026-08-11)
- **A shared GESTURE is shared as arithmetic, not as a component** - the two zoom models are not interchangeable, and "unzoom puts it back" is the one thing a user may assume. [posts](frontend/modules/posts.md#the-pinch-and-why-it-needs-a-focal-point)
- **A TLD-shaped ending cannot decide what is a domain in French** - an exact whitelist sidesteps the ambiguity instead of out-narrowing it (WP-LINK-1). [posts](frontend/modules/posts.md#autolinking-bare-domains-and-why-the-tld-shape-cannot-decide-it-wp-link-1)
- **AN ICON THAT CLEARS ITS FOUR SIDES IS STILL CROPPED BY EVERY CIRCULAR MASK** - a drawing's extremities sit on the DIAGONALS, so the inset a circle demands is far larger than the eye estimates: the canari reached 1.347 of its inscribed radius, and the obvious tenth off left it at 1.177, still outside. Measure the reach, do not pick a percentage. The margin belongs in the VECTOR, because a tab chip, a launcher and a rounded tile all scale the whole canvas and have none of their own to give - and the factor gets ONE home, since a second copy drifts from the drawing and the symptom is launcher icons a tenth too small on a surface nobody checks after a deploy. [logo-render.mjs](../../frontend/scripts/logo-render.mjs), pinned by `appIcons.test.ts` against the circle rather than the square.
- **A DECLARED COLUMN WIDTH UNDER `table-layout: fixed` IS A PROPORTION, NOT A SIZE** - unless the TABLE's own width is named too. Nine price columns declared at `8rem` inside a 1020px box measured 83-91px in Chrome, unequal and unreadable, which is the failure the declaration was added to fix. Name the total (`width: calc(var(--cols) * var(--col))`) and each column is exactly its size, the wrapper scrolls past it, and below it every column stretches by the same factor. Measure a table layout in a browser; the spec reading is not enough. [forms](frontend/modules/forms.md)
- **A UTILITY APPENDED AFTER A SHARED CLASS STRING DOES NOT WIN - TAILWIND ORDERS ITS OUTPUT, NOT YOUR ATTRIBUTE.** Competing utilities of one family are emitted in scale order, so `class="{controlClass()} py-2 text-sm"` lost to the `py-3 text-base` inside `controlClass`, silently, at three call sites that all looked deliberate. A size that can lose is worse than no size: a shared string takes a VARIANT (`controlClass(invalid, 'compact')`), never an override. [arch](frontend/architecture.md)

**Scrolling under a fixed bar** ([mobile](frontend/mobile.md#the-bottom-nav-reserves-nothing))

- **A `fixed` ELEMENT RESERVES NO SPACE, SO WHATEVER SCROLLS UNDER IT MUST RESERVE THE SPACE FOR IT** - and that reservation is a separate fact from the scroll, so cancelling the scroll cancels it too. `.page-scroll-wrap` reserved the bottom nav's height for every page; the chat shell zeroed that padding to be exactly one viewport tall, and took the reservation with it. Enumerate what a cancelled rule was CARRYING, never what it is named after.
- **A SCROLL THAT LEGITIMATELY CANNOT MOVE LOOKS EXACTLY LIKE A BROKEN ONE.** With nine tiles in a 744px box the content fitted, `scrollHeight === clientHeight`, and the browser was right to do nothing - while the bar hid the last row for good. The bug report said "scrolling is impossible" and was accurate; the defect was the unreachable content, not the gesture. Measure the container's geometry before touching the gesture handler, or you fix the wrong half.
- **A SPINNER IS A PROMISE THAT SOMETHING IS HAPPENING**, so a control with nothing to do must be able to DECLINE rather than resolve. The conversation list is push-fed and has nothing to fetch while the socket is up; its pull-to-refresh slept 600 ms and returned, which is a timeout standing in for work. Ask per gesture, not once at binding - whether there is work is a property of the moment.

**Announcing something once** ([core-service](services/core-service.md#the-admin-announcement-shown-once-per-account))

- **A filter that REFUSES is a gate, and the difference is what the caller learns** - three reasons, one `null`, on purpose.
- **A range with NO BOUNDS must not read the value it would have compared** - ask whether the discriminator is needed before demanding it be valid.
- **"Once per account" is a SERVER ROW or it is nothing** - and that row answers one question, "has this account seen X", never "is this account current".

**The one sentence a server may still write** ([chat-delivery](services/chat-delivery.md#the-one-sentence-this-server-still-composes-and-the-column-that-tells-it-the-language))

- **"THE DEVICE COMPOSES THE SENTENCE" IS THE RULE, AND THE EXCEPTION IS WHERE THE DEVICE COMPOSED NOTHING.** `push-content.ts` moved every social push to `contentKey` + `actorName` + `contentArg` and rejects a server-side `locale` column in writing - correctly, for the pushes it is about. `APNS_FALLBACK_BODY` is shown exactly when the iOS extension did NOT run, so there is no device-side composition to defer to and no `ctx.locale` was ever read. **Do not apply a decision to the case it was not measured over**: the repair there is to CARRY the discriminator (`push_token.locale`, written by the app that owns the preference), which is the same rule pointing the other way.
- **ADDING A FACT TO A REGISTRATION MEANS RE-VISITING WHAT DECIDES A REGISTRATION IS OWED.** The client skipped the POST when the FCM token was unchanged; `changeLocale` reloads the document and `sessionStorage` survives a reload, so the one registration that exists to record a language change is precisely the one that would have been skipped - silently, for as long as the token lived. The skip key is now `<token>|<locale>`, and every OTHER reader of that key had to be re-read too (one tests it for presence, which stays correct while its name no longer did).
- **A BUDGET COMPUTED ONCE FOR MANY DEVICES CONSTRAINS ANYTHING LATER SUBSTITUTED PER DEVICE.** The inline-ciphertext budget is measured, the ciphertext chosen, and only then the payload built per token - so a per-language body must never be able to exceed what the budget measured. Size on the LONGEST, derive it from the table rather than typing it, and pin it with a test that fills a payload to the budget and asserts every language still fits: sizing on the short language fails three tests, and would have shipped green otherwise.
- **AN APNs `loc-key` IS NOT A FREE VERSION OF THIS.** iOS resolves it against the app bundle and shows the RAW KEY when it does not resolve - it does not fall back to `body`, so sending both does not protect anyone. Any key-based repair is dated by the OLDEST INSTALL that can still reach the app, not by when the key was written.

**A vendor's name, and the one layer it is true in** ([payments](frontend/modules/payments.md#where-a-providers-name-may-appear-and-where-it-may-not))

- **A PROVIDER'S NAME IN A SHARED CONTRACT MAKES THE CONTRACT DEPEND ON ONE IMPLEMENTATION**, and nothing fails while that implementation is the only one. `PaymentProvider.getConnectAccountStatus` - the method `LydiaPaymentProvider` implements too - returned a `StripeConnectStatusResponse` imported from the Stripe module, so Lydia imported Stripe to declare its own return type. The SHAPE was already neutral; only the name was not. The type belongs in the contract, the derivation stays in the implementation and KEEPS the vendor's name, because `deriveStripeConnectStatus` really is Stripe's mapping.

## The edge -> [cloudflare-edge](infrastructure/cloudflare-edge.md), [nginx](infrastructure/nginx.md)

`edge` = [cloudflare-edge](infrastructure/cloudflare-edge.md), `nginx` = [nginx](infrastructure/nginx.md).

**Who owns a header**

- **nginx owns EVERY response header; the edge adds none** - the edge has no representation in git, so no review, test or deploy can see it change. [edge](infrastructure/cloudflare-edge.md)
- **A header two layers can set belongs to exactly ONE of them** - two `Access-Control-Allow-Origin` is malformed to every browser, and it fired only for the origins the allowlist RECOGNISES, so it broke local development and worked in production. `proxy_hide_header` before `add_header`. [nginx](infrastructure/nginx.md)
- **A policy that must be restated per block is declared ONCE and included** - `add_header` REPLACES the inherited set, and verbatim copies do not stay equal. [nginx](infrastructure/nginx.md)
- **A refusal expressed as a THROW is a 500, not a refusal** - `callback(null, false)`, never `callback(new Error(...))`. A policy layer that cannot say "no" without saying "broken" reports a fault the system does not have. [nginx](infrastructure/nginx.md)
- **A LITERAL in the compose file beats the `.env` the deploy writes, so the variable was never inert - it was UNREAD.** `ALLOW_ORIGIN: "*"` on the chat-gateway meant an allowlist CD had been writing for weeks reached nothing and the gateway answered every origin. Where a value must come from the environment, `${VAR:?...}` - a default is a policy nobody chose, and both available ones are wrong. [chat-gateway](services/chat-gateway.md#cors-the-list-is-a-fact-about-the-clients)
- **A variable read by two consumers with different SHAPES is one of them being wrong.** The same `ALLOW_ORIGIN` fed a comma-separated allowlist and three single-origin fields, which held all five entries as one origin each and never said so. A name says what a value IS; two shapes means two names. [chat-gateway](services/chat-gateway.md#the-variable-used-to-feed-three-consumers-that-wanted-a-single-origin)
- **An ORIGIN LIST IS VERIFIED BY READING THE SERVED HEADER, never by the deploy's colour** - a wrong origin parses fine and simply matches nothing, so only an EMPTY list is loud. And the list is a fact about the CLIENTS: a Tauri WebView calls the API cross-origin with one spelling per platform, and a missing spelling is an outage with no server-side error to show for it. [chat-gateway](services/chat-gateway.md#verifying-it-and-why-the-deploys-colour-is-not-the-proof)

**CSP, and why its failures do not look like CSP**

- **A second CSP header can only REMOVE permissions, never grant one** - the effect is the INTERSECTION, so a rule added to "loosen" a policy asserts the opposite of its only possible effect, and deleting it is provably safe. [edge](infrastructure/cloudflare-edge.md)
- **`*` matches NETWORK SCHEMES only** - never `blob:`, `data:` or `filesystem:`, so `connect-src *` is stricter than `connect-src 'self' blob:` for the case that matters. [edge](infrastructure/cloudflare-edge.md)
- **A permission to DISPLAY is not a permission to READ** - the half that is allowed is the visible half, so the feature looks alive and does nothing. [edge](infrastructure/cloudflare-edge.md)
- **A CSP refusal is indistinguishable from an ordinary failure, BY DESIGN** - only `securitypolicyviolation` names the directive, so build the probe on that event or it reports the theory it was written with. [edge](infrastructure/cloudflare-edge.md)
- **An allowlist is a DESCRIPTION OF THE CODE**, so it has a test that fails when the code calls a host it does not name. [edge](infrastructure/cloudflare-edge.md)

**Topology**

- **The account is the unit of audit, not the ZONE - and a second hostname can name the same destination.** The tunnel INGRESS table is the only listing that shows it; a DNS listing shows names alone. [edge](infrastructure/cloudflare-edge.md)
- **The single public entry point is also a single point of DISCONNECTION: a frontend redeploy cuts every proxied WebSocket at once.** So the reconnect ladder is exercised fleet-wide by every deploy, and **any measurement window that straddles a deploy explains its own fallout**. [WP-RECONNECT-1](frontend/modules/auth.md#wp-reconnect-1---the-ladder-that-stopped-and-the-two-silences-under-it)
- **Configuration assembled as TEXT is validated in the build, or it is validated by the outage** - `RUN nginx -t` costs a red pipeline instead of a site that will not start. [nginx](infrastructure/nginx.md)

- **A `singleTask` ACTIVITY HAS EXACTLY ONE INTENT, AND ANY LATER `am start` REPLACES IT.** `MainActivity.onNewIntent` calls `setIntent(it)`, and the deep-link plugin reads `activity.intent` in `load(webView)` to find the URL the app was STARTED with - so a plain launch fired while the WebView is still booting silently deletes a pending deep link. It is not a native-only trap: anything that "just brings the app to the front" is delivering an intent. Measured on COMM-18, where the RIG was doing it ([story](../../CHANGELOG.md)).

- **A TAURI APP HAS TWO HTTP STACKS AND ONLY ONE OF THEM IS THE WEBVIEW.** Page loads go through the WebView and honour Android's network security config; every `fetch` the app makes goes through the Tauri http plugin, which is Rust `reqwest` - and this build's `Cargo.lock` has `webpki-roots` with no platform verifier, so it trusts the bundled Mozilla roots and NOTHING the device was told to trust. A private CA installed for the WebView changes nothing there: TCP connects, then every request dies as `error sending request for url`. Anything that reasons about the app's network - a certificate, a proxy, a trust store, a scope - must say WHICH stack it is reasoning about ([story](../../CHANGELOG.md)).
- **AND THE TAURI CAPABILITY SCOPE READS AN EMPTY PORT AS THE PROTOCOL'S DEFAULT PORT.** `https://**` matches 443 and nothing else, so an HTTPS estate on any other port is refused by the app's own scope with `url not allowed on the configured scope` - which reads as a server fault and is not one.

- **A MENTION IS A TOKEN IN THE CIPHERTEXT, AND EVERY SURFACE THAT RENDERS TEXT OWES IT A RENDERER.** `@[<64 hex>]` is what is stored; the web splits it into a chip and the Android push handler printed it raw, so the highest-priority notification channel there is showed a sixty-four character blob. Nothing types a string as "already rendered", so the omission is invisible to the compiler and to review - the same shape as the Paraglide rule above it. **When a value has a display form, find every consumer of the raw form**, native ones included: they are the ones no web test reaches. And a renderer on a push path may not resolve names over the network - it labels what it can prove and says plainly that it cannot name the rest ([story](../../CHANGELOG.md)).

Push transports, the App Group, the NSE, the decrypt ladder and the update target are all on that
page. `mob` = [mobile](frontend/mobile.md), `auth` = [auth](frontend/modules/auth.md).

**A capability scope is a URL PATTERN, and a build profile is not one of its dimensions**

- **AN EMPTY PORT IN A URL PATTERN MEANS THE PROTOCOL'S DEFAULT PORT, NEVER "ANY PORT".** `http://**` matches port 80 and nothing else; `https://**` works only because 443 is https's default, which is what makes the pair look symmetric and hides the bug. A Tauri capability granting `http://**` therefore refused the local estate on `:8081` for every call the HTTP plugin made, and the product said so in red under the PIN field on a phone that had just logged in successfully. Spell the wildcard - `http://localhost:*` - and validate a pattern against a REAL url before believing it. [cross-client-campaign-resume](cross-client-campaign-resume.md)
- **A CAPABILITY FILE IS COMPILED INTO EVERY BUILD UNLESS THE CONFIG NAMES A SUBSET, AND ITS DESCRIPTION IS NOT A MECHANISM.** `development.json` said "NOT included in production builds" and shipped in all of them: `Capability` has no dev/release switch (its only filter is `platforms`, by target OS), and an absent `app.security.capabilities` means ALL files are included. A dev-only scope is made opt-in by naming the subset in `tauri.conf.json` and adding the extra capability through a `--config` overlay that only a debug build passes. Verify which way it went by grepping the built artefact for the scope string, never by reading the intent. [cross-client-campaign-resume](cross-client-campaign-resume.md)

**A phone is not THE phone once there are two**

- **A RESOLVER THAT PICKS "THE FIRST ONE" IS CORRECT UNTIL THE POPULATION IS TWO, AND THEN IT IS SILENTLY WRONG.** `serial()` took the first USB entry adb listed; a second phone was attached and it answered the other one, so every gesture would have woken, forwarded, logged into and measured a device the run was not about while reporting confidently about the first. Ambiguity in a device selector is an ERROR, resolved explicitly (a name -> serial map, or the tool's own `ANDROID_SERIAL`), never a choice made for the caller. [cross-client-testing](cross-client-testing.md)

**A placeholder is not an identity**

- **A VALUE THE SENDER DEFINES AS "NOT AN IDENTITY YET" MUST BE REFUSED AT BOTH ENDS, AND A SHAPE ALLOWLIST IS NOT AN IDENTITY ALLOWLIST.** `unknown` and `pending` are what a Canari client holds before its session resolves; on 2026-08-27 one of them was stored as an `active` member of a real conversation 0.84 s before its real members joined, and held the peer's place for 134 minutes while both directions of it were lost. Both literals pass the regex perfectly, and the ghost gate that exists for this class passed too, because the placeholder had registered a KeyPackage. Refuse the VALUE, on every path that can write an identity, on the client and on the server - a client of any version reaches the endpoint. [backlog](backlog.md)
- **A CLASS THAT GUARDS ON A SENTINEL IN THREE PLACES AND PUBLISHES IT IN A FOURTH HAS NAMED ITS OWN DEFECT.** `BaseMlsService` compared against both literals in `settleBarrier`, `fetchPendingMessages` and `resolveDeviceId`, so the value was known to be a non-identity - and one seam sent it to the server anyway. When a sentinel is worth a guard anywhere, it is worth a NAMED CONSTANT and an enumeration of every site that can emit it; a literal repeated by hand is a guard that will be forgotten exactly once. [backlog](backlog.md)
- **A GREEN LADDER PROVES THE SYMPTOM, NEVER THE ROSTER.** Two hundred campaign rows asserted that messages appear, badges light and lists are right; exactly one read the membership table at all, and it read WHO was named rather than WHAT STATUS they held. All of them would have passed through a conversation whose member was a placeholder. When a mechanism has durable state, ONE row must assert that state directly - and one must ask it of the whole population, because three of the stranded rows had stood twenty-five days and no per-session test can see an age. [testing-methodology](testing-methodology.md)

**One value, two stores**

- **WHEN ONE VALUE LIVES IN TWO STORES, THE ORDER THEY ARE READ IN IS A CORRECTNESS PROPERTY, NOT A PREFERENCE - AND THE ANSWER IS DECIDED BY WHICH ONE THE WRITER TOUCHED LAST, NEVER BY WHICH IS SAFER.** The push secret sits in `pending_push_secret.txt` and in the Keystore; the file is written by the WebView at every `/register` and the Keystore only ever at a process start or resume, so the file is newer BY CONSTRUCTION whenever it exists. Reading the Keystore first - because a Keystore is the "real" store - returned a secret the server had already invalidated, for the whole life of a process, and every background send in that window got a 403. The function's own doc comment named the race and the `if (stored != null) return stored` above it made that branch unreachable in exactly the case it described. Enumerate who writes each store and when; the later writer wins. [mobile](frontend/mobile.md) [backlog](backlog.md)
- **THE LIFECYCLE THAT HEALS A DEFECT IS THE ONE YOU MUST NOT MEASURE ON.** Killing the app is the intuitive way to prove a background path, and it is the branch that starts a fresh process, runs `onCreate`, migrates the pending secret and repairs the very state under test. The killed run returned `HTTP 201` and the backgrounded run returned `HTTP 403` ninety seconds later on the same build, device and conversation. A check that says "kill the app" must say WHY killing is the interesting state, and a background path owes a BACKGROUNDED run as well - `am kill` and HOME are two different questions, not two ways of asking one. [device-verification](device-verification.md) [testing-methodology](testing-methodology.md)
- **A NOTIFICATION ACTION IS CONSUMED THE INSTANT IT FIRES, SO "LEAVE THE NOTIFICATION UP AS THE RETRY AFFORDANCE" IS NOT A DISPOSITION.** Android replaces the `RemoteInput` row with an indeterminate spinner and never resolves it; doing nothing on failure leaves a notification that reads "sending" for ever and has no actions left to press. A failure path that owns a piece of system UI must RE-POST it, and re-posting is not cancelling - the queued send stays queued. [mobile](frontend/mobile.md)

**What a notification action knows, and what it must not go looking for**

- **A FACT THE TRIGGER ALREADY HOLDS MUST BE CARRIED, NOT RE-DERIVED FROM A CACHE WRITTEN FOR SOMETHING ELSE.** The shade's "Marquer comme lu" needed to name what it was acknowledging, and went to `fcm_message_cache.ndjson` for the message ids - a file `consumeFcmCache()` CLEARS at every app boot. Whenever the app had been opened since the notification arrived, the list was empty and the action sent NOTHING, with no error, because an empty list is indistinguishable from a conversation with nothing to acknowledge. The notification itself knew the answer all along; it is now stamped into the action's intent. This is the same rule as A COLUMN IS ONLY EVIDENCE FOR THE QUESTION IT WAS WRITTEN TO ANSWER, met from the other side. [mob](frontend/mobile.md#acknowledging-a-conversation-from-the-notification-shade)
- **A CONTROL FRAME REACHES THE OTHER SIDE, WHICH IS NEVER THE SIDE THAT SENT IT.** MLS does not echo a message back to its author, so a state change a background action broadcasts arrives everywhere EXCEPT the device the user is holding. Marking a conversation read from the shade cleared every peer's badge and left the acting phone's own - which reads exactly like the button doing nothing. When a native action mutates shared state, ask separately how THIS device learns of it; here that is `read_watermarks.ndjson`, merged at the next login. [mob](frontend/mobile.md#acknowledging-a-conversation-from-the-notification-shade)
- **AN INSTANT THAT MERGES BY `max` MAY NEVER COME FROM THE ACTING DEVICE'S CLOCK.** A read watermark taken from `System.currentTimeMillis()` on a phone running fast marks messages read that nobody has seen, permanently and unfixably, on every device in the conversation. It is taken from the MESSAGES - the sender's `sentAt`, carried down from the push - exactly as `watermarkAfterReading` does in the foreground. Where it is unknown the action says nothing rather than substituting a clock. [mob](frontend/mobile.md#acknowledging-a-conversation-from-the-notification-shade)
- **A NAME-MATCHING CLASSIFIER WHOSE FALLBACK IS USER-VISIBLE IS A NOISE GENERATOR WAITING FOR ONE NEW NAME.** `format_system_event_text` silenced seven control events by name and showed everything else as `evenement de groupe (<event>)` - so `read_watermark`, `channel_invitation` and the six history-sync frames were all one non-silent push away from being notifications. They were unreachable only because control frames are sent `silent`, which is a property of a DIFFERENT layer. Enumerate the vocabulary against its producers and pin it with a test; a fallback that renders raw protocol at the user is not a fallback. [mob](frontend/mobile.md)

**Where the platform is not the web**

- **A WEBVIEW'S USER AGENT IS NOT A FACT ABOUT THE DEVICE, AND ON AN iPAD IT IS FLATLY FALSE.** WKWebView's default content mode is `.recommended`, and above 375 px that means DESKTOP-CLASS browsing: the WebView announces `Macintosh; Intel Mac OS X 10_15_7` and names no Apple device at all. `/iphone|ipad|ipod/` was therefore false on every iPad ever to run this app, which took the WEB side of six different iOS decisions - the OIDC redirect URI among them, so it asked Authentik for `tauri://localhost/auth/callback`, which any provider must refuse. App Review found it on an iPad Air and rejected the submission (2026-08-30); Authentik's access log holds the request, user agent and all. The platform is a COMPILE-TIME constant the native side already carries: READ it (`tauri-plugin-os`), never parse it out of a string the OS is free to rewrite for its own reasons. [mob](frontend/mobile.md#the-ipad-that-called-itself-a-macintosh-and-the-login-app-review-could-not-finish)
- **AND A DEVICE CLASS NOBODY OWNS IS A PLATFORM NOBODY TESTS.** Every iOS measurement this repo has ever taken was on one iPhone, so a defect that needed a WIDE screen to appear survived hardware verification, a full parity audit and two store submissions. When a check says "iOS", write down which DEVICE it ran on - the answer is what the check actually proved. [device-verification](device-verification.md)

- **A FRAMEWORK'S AUTOMATIC HOOK HAS A PRECONDITION TOO, AND "it installs itself" USUALLY MEANS "it looks ONCE".** Firebase's App Delegate Proxy is configured, documented and explicitly enabled in `Info.plist` - and it installed nothing, because it reads `sharedApplication.delegate` at configure time under a `dispatch_once`, and `[FIRApp configure]` runs from `main()` before `ffi::start_app()` creates the application. Every iPhone dropped its APNs token on the floor for the platform's whole life. When a hook is the bridge for something load-bearing, ask WHEN it samples the thing it hooks, and prove the thing existed then. [mob](frontend/mobile.md#the-apns-token-had-nowhere-to-land-because-the-proxy-meant-to-catch-it-installed-nothing)
- **CODE THAT WORKS AROUND AN ABSENT FRAMEWORK HOOK IS EVIDENCE THAT HOOK IS ABSENT EVERYWHERE, not only where it was worked around.** `canari_push.mm` already swizzled wry's delegate by hand for remote notifications and called `appDidReceiveMessage:` by hand - two jobs the proxy does when installed. The file had recorded the proxy's absence for months; nobody read it as a statement about the token. A hand-rolled substitute is a measurement: go and find everything else that mechanism was supposed to carry. [mob](frontend/mobile.md#the-apns-token-had-nowhere-to-land-because-the-proxy-meant-to-catch-it-installed-nothing)
- **A KEYBOARD IS ANSWERED BY MOVING THE LAYOUT VIEWPORT, NEVER BY ADDING A MARGIN** - on both platforms, for the same reason and with the same two faces. A margin leaves the document taller than the shell, so the composer hides AND an empty band appears on scroll; resizing makes the band impossible instead of hiding it. iOS shrinks the WKWebView's frame, Android pads the content view; the web layer's `layoutInsetBottom` was already written to stand down when either happens. [mob](frontend/mobile.md#ios-shrinks-the-webview-and-that-is-the-same-decision-taken-twice)

- **A gate inside a component's own `onclick` is dead code wherever something else already owns the event** - gate the ONE function both paths call. [mob](frontend/mobile.md)
- **`fetch` is not `fetch` in the WebView**: the routing rule names what the plugin CAN do, never the exceptions. [mob](frontend/mobile.md#fetch-is-not-fetch-inside-the-webview)
- **A relative `/api/` path is dead on mobile, and it fails as a SUCCESS** - 200 with an HTML body. [mob](frontend/mobile.md#a-relative-api-path-is-dead-on-mobile-and-it-fails-as-a-success)
- **AND AN `<img src="/api/…">` IS THE SAME DEFECT WITH NO WITNESS AT ALL.** A `fetch` at least hands a caller something to misread; an image handed `index.html` fails to decode, fires `onerror`, and any component with an initials placeholder shows the placeholder - nothing thrown, nothing logged, no request in any log that looks wrong. The Carte de la Vie Asso shipped with every president photo and every association logo missing on mobile, and two more call sites had it. Wrap the path in `apiAssetUrl()`; `apiUrl.absolute.test.ts` now scans for `src=` as well as `fetch(`. [mob](frontend/mobile.md#a-relative-api-path-is-dead-on-mobile-and-it-fails-as-a-success)
- **AND THE SAME DEFECT ONE INDIRECTION OVER IS INVISIBLE TO BOTH OF THOSE SCANS.** The offending path need never appear in the source: the backend stores a card icon as `/api/media/public/<id>?v=...` and the component binds `src={card.iconUrl}`, so there is no literal `/api/` to grep and no `fetch` to inspect - only the same silent placeholder. `CardTile` shipped that way and took all five card lists (shop, association detail, partnerships, boutique, both manage tabs) down on mobile only; `CardIconEditor` had it too and was found by the new TEST rather than by reading, having left a president re-uploading an icon that had uploaded fine. **When the value arrives at runtime, the guard is the FIELD NAME the backend stores it under** - `apiUrl.absolute.test.ts` scans for a raw `iconUrl`/`logoUrl` bound into `src` as its third check. Absolutize in the SHARED component, not at the call sites, or the next caller repeats it. [mob](frontend/mobile.md#a-relative-api-path-is-dead-on-mobile-and-it-fails-as-a-success)
- **A TEACHING GUARD MUST COVER THE WHOLE SHAPE, NOT THE ONE SPELLING THAT BIT LAST TIME.** The rule above had a scanner, and the scanner matched `fetch(` only - so the identical mistake spelled `src=` walked past it three times. When a test exists to stop a class of defect, ask which other syntax expresses the same class before believing it is covered.
- **AN ASYNC `onMount` CANNOT RETURN A TEARDOWN.** Svelte honours a returned cleanup only from a SYNCHRONOUS `onMount`; from an async one the return value is a promise and the subscription is never detached. Use `$effect` for anything that must be torn down.
- **A WebView has no download manager**: `<a download>` is a silent no-op that still "succeeds". [mob](frontend/mobile.md)
- **An app extension has its own data container** - the App Group is the only shared storage. [mob](frontend/mobile.md)
- **A native thread has no Java frames**, so `FindClass` reaches framework classes only. [mob](frontend/mobile.md)
- **Edge-to-edge is not guaranteed by `env(safe-area-inset-*)` alone** - call `enableEdgeToEdge()` explicitly. [mob](frontend/mobile.md)
- **A POLICY FILE NOTHING REFERENCES IS NOT A POLICY, IT IS A DESCRIPTION OF ONE.** `data_extraction_rules.xml` excluded every byte from device transfer for as long as it existed, and was wired to nothing; a shrinker's reachability report is the cheapest enumeration of what an app declares and never consults. [mob](frontend/mobile.md#plays-q3-2026-quality-requirements-measured-against-this-app)
- **`allowBackup="false"` DOES NOT STOP A DEVICE-TO-DEVICE TRANSFER** on Android 12+, and an absent `<device-transfer>` section means that mode carries EVERYTHING. Two attributes, two API ranges, both required. [mob](frontend/mobile.md#plays-q3-2026-quality-requirements-measured-against-this-app)
- **A DECODE SIZED BY ITS INPUT IS UNBOUNDED WHEN THE INPUT IS NOT YOURS.** Read the header first and sample down to the size the platform will draw - and count the SECOND allocation a crop or a scale adds. [mob](frontend/mobile.md#the-face-on-a-notification-and-what-happens-when-there-is-none)
- **A CSS custom property consumed at two nesting depths applies its correction twice**; delete the second consumer. [mob](frontend/mobile.md)
- **`will-change: transform` ON AN ANCESTOR MAKES IT THE CONTAINING BLOCK FOR `position: fixed` DESCENDANTS, PER SPEC - AND ON REAL MOBILE BROWSERS THAT DESCENDANT CAN LOSE ITS OWN COMPOSITING LAYER MID-SCROLL AND VANISH UNTIL THE NEXT REFLOW.** A form's payment bar, `fixed` inside `.page-scroll-wrap` (which carries `will-change: transform` for swipe-nav), scrolled away and never came back on its own - reproduced live on-device, not in a simulator. `position: sticky` is not redirected by a transformed ancestor the same way and does not carry the failure mode; it also never leaves the document flow, so nothing needs to manually measure or reserve its height the way `fixed` does. When a floating element needs to survive scrolling under a `will-change: transform` ancestor, reach for `sticky` before `fixed`.
- **`env(safe-area-inset-bottom)` CAN ANSWER NON-ZERO IN A PLAIN MOBILE BROWSER TAB, NOT ONLY IN THE NATIVE EDGE-TO-EDGE WEBVIEW** - measured non-zero on at least one device. Only Tauri draws behind the OS gesture/button area and needs the real inset; a browser tab already excludes that area from its own viewport, so applying the raw value there opens a dead gap above the browser's own on-screen nav buttons. Fifteen call sites called `env()` directly; centralized into one `--safe-area-inset-bottom` CSS variable, decided once via `window.__TAURI_INTERNALS__` in `app.html`'s inline script before first paint (same pattern as the theme-flash guard already there), so every consumer reads `var(--safe-area-inset-bottom, 0px)` instead of asking the platform question itself.
- **TWO VALUES NAMING THE SAME QUANTITY, COMPUTED TWO DIFFERENT WAYS, ARE NOT GUARANTEED TO COMPARE EQUAL - AND AN EXACT COMPARISON BETWEEN THEM CAN FAIL FOREVER, NOT JUST OCCASIONALLY.** A scroll-position check compared a CSS `calc()` reservation against an independently measured `clientHeight`, both nominally `4rem + safe-area` - live inspection over the Chrome DevTools Protocol on the actual device found the sentinel's measured `top` sitting 0.05px past the threshold AT THE PHYSICAL MAXIMUM SCROLL POSITION, meaning the exact `<=` comparison could never once be satisfied, on any device, no matter how far the user scrolled. A few pixels of tolerance is not sloppiness here; it is the only way to admit sub-pixel rounding that two independent computations of the same nominal value will always be subject to. Suspect this whenever a geometry check "almost always" or "never" fires despite the underlying condition plainly being true - measure the actual gap before guessing at a fix. [mob](frontend/mobile.md#reading-live-state-out-of-a-running-webview-over-adb) has the CDP-over-adb recipe used to catch it.
- **A plain system-browser launch is an ORPHANED activity on Android** - a Custom Tab shares the app's task. [mob](frontend/mobile.md)
- **A SERVER'S ORIGIN ALLOWLIST IS A FACT ABOUT ITS CLIENTS, AND A TAURI CLIENT HAS ONE ORIGIN PER PLATFORM.** `http://tauri.localhost` on Android and Windows, `tauri://localhost` on iOS, macOS and Linux. Four Nest bootstraps spelt only the Android pair inline, so iOS's login died in `POST /api/auth/oidc/callback` while the deep link, the Custom Tab and the authorization code were all perfectly intact. Name the list once, per service, in `cors-origins.ts`. [mob](frontend/mobile.md#the-ios-login-that-died-in-a-cors-allowlist)
- **A DENIED CORS PREFLIGHT ANSWERS 404, NOT 403 - AND THE CLIENT IS TOLD NOTHING AT ALL.** A `cors.origin` callback answering `false` correctly omits the headers, but it also declines to short-circuit the `OPTIONS`, which then falls through to a router that has no handler for it. The server logs a 404 on a path that exists, the browser reports a bare `TypeError: Load failed` (WebKit's wording for every network-layer refusal, CORS included), and the ONE fact that identifies the client - the origin it presented - appears in no log on either side. **A CORS refusal must therefore log the origin it refused**, once per distinct value. [mob](frontend/mobile.md#the-ios-login-that-died-in-a-cors-allowlist)
- **PLATFORM PARITY IS NOT A PROPERTY OF THE NATIVE PROJECT.** The iOS build had its entitlements, its associated domains, its NSE, its App Group, its keychain sharing, its `CFBundleURLTypes` and an `apns` block beside every `android` one - and the platform still could not log in, because the asymmetry was in a server bootstrap nobody reads as mobile code. When auditing parity, sweep every place a platform is NAMED, starting with the ones furthest from the platform. [mob](frontend/mobile.md#the-ios-login-that-died-in-a-cors-allowlist)
- **A COOKIE THE NATIVE SHELL DEPENDS ON IS THIRD-PARTY BY CONSTRUCTION**, because the document's origin is the shell's and the cookie's is the backend's. Android blocks those by default and needs one explicit opt-in (`setAcceptThirdPartyCookies`, `MainActivity.kt`); **WKWebView blocks them too and exposes no equivalent API**, so an iOS session that survives a restart cannot be assumed from Android's working one. [sessions](sessions.md#third-party-cookies-and-the-shell-that-is-not-the-backend)

**What a lock, a boot or a push can do to a fact**

- **Work guarded by one lock is already serial - giving it a thread each only adds the fight.** Serialising it adds no latency. [mob](frontend/mobile.md)
- **A lock timeout is not a domain answer.** Any predicate that can FAIL TO LOOK needs a third value, and `UNKNOWN` reaches no recovery. [mob](frontend/mobile.md)
- **A dependency can make your process start in a state you never designed for** - read the MERGED manifest. [mob](frontend/mobile.md)
- **A destructive repair must be gated on knowing the state is really broken**, or a temporary condition becomes a permanent loss. [mob](frontend/mobile.md)
- **A destructive control exposed to the user needs an ALLOWLIST of what it may touch, not a denylist.** [mob](frontend/mobile.md)
- **AND IT KEYS ON THE IDENTITY THE DESTRUCTIVE API ITSELF USES**, never on a rendered abbreviation and never on ordinal position. `purge-devices.mjs` matched row text the product does not render, so every row read as the empty string and its denylist matched nothing - one reorder from deleting the campaign's only phone. The short device id shown to a human is `slice(0, 8)`, identical across a user's web devices; the full id was in the row's `title` the whole time. [testing](cross-client-testing.md)
- **Background decrypt applies no commit**, so a silent commit push leaves the next message unreadable - that is the epoch gap. [mob](frontend/mobile.md)
- **A decision reachable from the CLEARTEXT push fields must never sit behind the decrypt ladder.** [mob](frontend/mobile.md)
- **A PRECONDITION ONE PLATFORM DOES NOT HAVE IS STILL A PRECONDITION, AND A MIRRORED CALL INHERITS THE ORDER OF THE PLATFORM IT WAS COPIED FROM.** Android reads its FCM token at launch with no precondition; iOS cannot mint one before an APNs token exists, which arrives strictly after `registerForRemoteNotifications`. The iOS force-fetch, written as Android's declared mirror, sat in the launch bootstrap and could therefore only ever fail - for the platform's entire life. Carry the call to where the precondition is KNOWN to hold (`didBecomeActive`), and check it there rather than handing the work to a layer certain to refuse it. [mob](frontend/mobile.md#the-fcm-token-an-iphone-could-never-obtain-and-the-silence-that-hid-it-for-the-platforms-life)
- **THE ABSENCE OF A ROW IS NOT A REPORT - IT IS INDISTINGUISHABLE FROM A DEVICE NOBODY OPENED, AND THE HEALTHY COHORT STANDS IN FOR THE SILENT ONE.** `push_token` held 49 `android` rows and had never held ONE `ios` row: no alert, no mention and no CallKit ring had ever been deliverable to an iPhone, and nothing anywhere said so, because the client's only witness was a `console.warn` in a console that cannot be opened on that platform from this machine. **A capability that fails to arrive must report to somewhere a person reads, naming its cohort**, so one `GROUP BY` answers what a CORS incident had to stumble into. And it reports once, at the END of the retry ladder - an early failure the next attempt fixes would file a defect against a device that goes on to work. [chat-delivery](services/chat-delivery.md#a-device-that-cannot-get-a-push-token-at-all)
- **What removes a notification must key on what the POSTER wrote - and on iOS there are two posters.** [mob](frontend/mobile.md)

Permissions and `github.event_name` were both wrong in the same refactor, in files that never mentioned each other. [cicd](cicd.md#package-2-publishing-a-release-releaseyml---the-one-entry-point)
- **WHEN A HUMAN MAKES TWO INDEPENDENT STATEMENTS ABOUT ONE FACT, SOMETHING MUST COMPARE THEM, OR THE CONSUMER THAT READS ONLY ONE DECIDES ALONE.** A GitHub release carries a version string AND a "Set as a pre-release" checkbox, and they are supposed to be the same fact. Only the version was read, because the `published` event fires for both kinds and the checkbox was therefore invisible: ticking it on a `v0.17.0` deployed PRODUCTION, and forgetting it on a `v0.17.0-alpha.1` pushed a tester build to both store production channels - neither visible in a green run, and the second only billed a release later, when a mis-filed alpha became the change detector's baseline and services that HAD changed were reported unchanged. **The fix was not an assertion, it was picking a source that carries both**: `prereleased` and `released` fire for exactly one kind each, so both statements arrive and the mismatch becomes a refusal. [cicd](cicd.md#package-2-publishing-a-release-releaseyml---the-one-entry-point)

- **A PROBE THAT DECIDES A REDIRECT MUST BE AWAITED, NOT FIRED AND HOPED FOR.** The admin layout resolved its BDE tiers in the background and then decided, synchronously, whether to bounce the visitor - so the user the probe was meant to admit was thrown out whenever the request lost the race. Background is right for an item that can APPEAR late; it is never right for a gate. [admin](frontend/modules/admin.md)
- **A TIER'S PREDICATE LIVES WHERE EVERY SURFACE CAN CALL IT, OR THE SECOND SURFACE INVENTS A NARROWER ONE.** "May this user moderate content" was private to `moderation.controller.ts`, so the post controls wrote `isGlobalAdmin` instead - and a BDE holding `MODERATE` could delete a reported COMMENT while unable to touch the post around it. It is now `isContentModerator` on the service, like `isUserBdeAdmin` before it. [association-permissions](association-permissions.md)
- **WHAT IS PUBLISHED IN AN ASSOCIATION'S NAME BELONGS TO THE ASSOCIATION, NOT TO THE ACCOUNT THAT TYPED IT.** Editing and deleting such a post follow `POST_AS_ASSO`, so any officer may correct it and a former officer may not - authorship grants nothing extra once the byline is not a person. Nobody loses anything: publishing already required that flag. [association-permissions](association-permissions.md)
- **A second surface for an existing action mirrors the SERVER's rule, not the first surface's** - a `VALIDATE_EVENTS` holder had the right and nowhere to use it.
- **What a modal hides because it is redundant is a decision of the PAGE, never of `canEdit`.**
- **A RIGHT THE SERVER ACCEPTS AND NO LIST SHOWS IS REACHABLE ONLY BY SOMEONE WHO ALREADY KNOWS THE URL.** `assertFormManager` accepted `MANAGE_FORMS` on the linked association for months while `/forms` listed only what the caller owned. When a permission is added to a server-side check, enumerate the screens that must then show its subjects. [forms](frontend/modules/forms.md)
- **A DISABLED CONTROL CLAIMS SOMEONE WITH MORE RIGHTS COULD USE IT.** For a value that is immutable by DESIGN rather than by permission, render text, not a greyed-out picker.
- **A MATRIX HAS NO PRIORITY RULE TO GET WRONG; AN ORDERED RULE LIST IS NOTHING BUT ONE.** When several attributes select a value, express them as DIMENSIONS and take the cross product - exactly one cell then applies to anybody, and completeness becomes a save-time invariant instead of a runtime hope. The user's own correction to a design that had ordered rules. [forms](frontend/modules/forms.md)
- **A DIMENSION IS A PARTITION, NOT A FILTER** - so every criterion generates an undeletable `others` bucket. A dimension that only names the cases someone thought of leaves the rest unpriced, and the cross product explodes the moment a bucket may overlap another. [forms](frontend/modules/forms.md)
- **A VALUE THAT SELECTS A CELL MUST NOT ALSO ADD TO IT.** An answer used as a pricing dimension carries no additive supplement, enforced server-side: the cell already holds that choice, so the supplement charges it twice and nothing in the UI would say so. [forms](frontend/modules/forms.md)
- **A CLIENT-ONLY CONDITION IS NOT A CONDITION.** `dependsOn` was evaluated in the browser alone, so the server enforced `required` on questions the client never showed and charged the price modifier of answers it should have discarded. Any rule that decides what is REQUIRED or what is CHARGED is evaluated where the money is. [forms](frontend/modules/forms.md)
- **TWO CONDITIONS ON ONE SUBJECT ARE ANDED, NEVER CHOSEN BETWEEN.** When a legacy shape and its generalisation can both be present, translate one into the other and merge - preferring either drops a requirement silently. One evaluator, or the two come to disagree. [forms](frontend/modules/forms.md)
- **ONE PREDICATE FOR PRICE, VISIBILITY AND ACCESS.** The same `AudienceCondition` gates who may submit, who sees a question and what a person pays; a second implementation of "who is this person" is how a form reserved to one promo ends up with a price for a promo it excludes. [forms](frontend/modules/forms.md)
- **A USER-VISIBLE SENTENCE IN A COLUMN IS UNTRANSLATABLE BY CONSTRUCTION, AND NO COMPILER WILL SAY SO.** `submitLabel` held 'Envoyer' because the code that wrote it typed it, and Paraglide cannot see inside a database. Before storing any displayed text, ask who authored it: if the answer is "this code did", it is a message key, not data. If a human really authors it, store a translated map. [forms](frontend/modules/forms.md), migration `052`
- **A SERVER REFUSAL A MANAGER CAN REACH BY FLIPPING A SWITCH MUST BE CAUGHT BEFORE THE REQUEST.** The 400 is correct and its sentence is developer prose about a document; the screen owes a localized message naming the form or the question. [forms](frontend/modules/forms.md)

## Calls, and their record -> [call-service](services/call-service.md#the-call-record)

- **A failure seen in HALVES is attributed by the one witness that sees both, or not at all** - the SFU is that witness, so its record carries what separates the causes it cannot itself distinguish, one line per socket.
- **`duration_ms` alone cannot say whether a call happened** - it is read next to `connected_ms`, and `connected_ms=-` is a STATEMENT, never a missing value.
- **A disposition is set ONCE and the first cause wins** - recording the last event reports the consequence and hides the cause.
- **Counts at the END of negotiation, never a line per candidate** - and build the terminal ICE line out of the same helper as the record so the two cannot drift.
- **A per-device guard on a FAN-OUT reports a fleet fault when the fault is ours** - check the one thing every device depends on ONCE, before the loop, and never `break` out of a fan-out that returns a count.
- **Dropping an `RTCPeerConnection` is not CLOSING it** - webrtc-rs holds the TURN allocation until told to let go, and a "session end" line emitted while it is live states an end that has not happened.

## Presence, in the gateway -> [chat-gateway](services/chat-gateway.md#presence)

- **The presence key is per DEVICE and every event that removes it is per CONNECTION** - two tabs are one device, so any deleter must discount its own connection and check for survivors. `AppState::remove_session` / `has_other_sessions` are the only two forms of that question; a third call site writing its own is the bug.
- **A connection is identified by its `conn_id`, never by `is_closed()`** - an aborted send task still reports `false` until the runtime drops its receiver.
- **PRESENCE ANSWERS "IS A SOCKET OPEN", AND THAT IS NOT "CAN THIS DEVICE BE GIVEN WHAT IT ASKED FOR".** A cold-started client has authenticated HTTP well before it has a WebSocket: measured 2026-08-25 (COMM-18), the phone registered for push, landed an accepted commit and published a GroupInfo across sixteen seconds in which the gateway logged no reconnect for it, so the presence key was truthfully absent while the device was demonstrably alive. The answer to its own seed request was discarded in that window, permanently, because a transport-only frame is dropped for recipients presence reports offline. **The reachability of a rendezvous's requester is carried by the REQUEST - which arrived, and named its answerer - and must never be re-derived from a socket at answer time.** The fix for such a read is to delete it, not to make it more accurate: a more accurate liveness clock is still the wrong question. ## Sessions, in every app -> [sessions](sessions.md)

Settled 2026-08-04 (WP-SESS-1, WP-SESS-2), SHIPPED in all four apps. Read [sessions](sessions.md)
before touching any login, cookie or rotation.

- **A cookie whose content IS the identity it claims is not a credential, it is a form field.**
- **A replayed rotating token is TWO holders of one cookie** - revoke the session, with a grace window, and settle the race in ONE conditional `UPDATE`.
- **An empty key can fail OPEN or CLOSED and you cannot guess which.** Decide explicitly.
- **Rotation makes DURABILITY part of the protocol** - force the write where the rotation happens and AWAIT it; on Android the cookie jar reaches disk only on `CookieManager.flush()`.
- **A dead session is an ANSWER** - never retry the request anonymously, or "you are logged out" renders as "there is nothing here". Reach the verdict in ONE place.
- **A one-shot announcement and a late subscriber are a RACE** - replay the verdict to whoever registers after it, because a fallback never does everything the real handler does.
- **A ONE-SHOT GUARD MAY COVER ONLY THE PART THAT MUST HAPPEN ONCE.** Releasing whoever is waiting RIGHT NOW is not the logout: "has a logout already run" is true once per expiry, "does this submit need its modal closed" is true again every time. Gating both on one flag left a PIN modal that no correct PIN could ever answer, and a 10 s watchdog then invented "please try again" for a latch that is permanent by design ([story](../../CHANGELOG.md)).
- **"CAN THIS ENGINE KEEP A COOKIE" AND "CAN THIS DEPLOYMENT ISSUE ONE IT WOULD KEEP" ARE TWO QUESTIONS, AND A TRANSPORT PREDICATE THAT ASKS ONLY THE FIRST IS RIGHT ON PRODUCTION AND WRONG EVERYWHERE ELSE.** `None` requires `Secure` and `Secure` requires TLS, so a plain-HTTP stack can only issue `SameSite=Lax` - and **a `Lax` cookie cannot be SET in a third-party context at all**. A native shell's page is its own origin, so it is third-party by construction: it was handed a cookie it discarded on arrival and logged itself out before enrolling, while the same build was provably fine against HTTPS. A browser on `localhost` never sees any of it, being same-site with itself. **When a client "logs in and then logs itself out", compare its PAGE origin with its API origin, and check what the API's scheme lets the server issue** ([story](../../CHANGELOG.md), [sessions](sessions.md#the-credential-a-client-carries-itself)).
- **THE ACCESS TOKEN NAMES THE USER; ONLY THE REFRESH CREDENTIAL NAMES THE LOGIN - so EVERY request the server answers from the SESSION has to carry it the way that platform carries it.** Where a native shell cannot keep the cookie the credential travels in a header, and `auth.ts` sent it on `refresh` and `logout`; the four endpoints of `authSessions.ts` sent it on none, and the server's fallback then read the cookie the WebView still happened to hold - **by construction a value the client stopped maintaining**, since rotation goes through the header. Measured on DEL-7, 2026-09-05: `refresh` 200 at 04:02:40, `PUT sessions/current/device` 404 thirteen seconds later naming a sid absent from the table, while the rotated session was alive. **The cost is never the log line**: `bindCurrentSessionDevice` is the ONLY writer of `auth_sessions."deviceId"`, whose purge of unreachable sessions claiming a device is what closes the reinstall hole - so on the native shell that hole never closed - and `revokeOtherAuthSessions` hands the server the same id as the one to KEEP, so unresolvable it left "sign out everywhere else" with no reason to spare the caller. **Enumerate by what the SERVER reads, never by which call felt session-shaped.**
- **AN ERROR SEAM THAT OFFERS A RETRY MAY ONLY BE USED WHERE THERE IS SOMETHING TO RETRY.** `onLoginFailed` and `onSessionExpired` differ in exactly that, and the caller BINDS them to different things - the first to a PIN prompt, the second to a logout and a redirect. A revocation announced through the first reopened a PIN prompt on a device the line above had just returned to a fresh install, and the page then sat on `/chat` with no session until the prompt's own attempt drew a 401 ([story](../../CHANGELOG.md)). Pick the seam by what the user can DO next, never by the fact that something failed.

## Object storage, and deleting infrastructure -> [docker](infrastructure/docker.md)

- **A COUNT is not a COMPARISON** - compare the KEY SETS, both directions. Ours held 306 against 200 and was still missing five.
- **A rollback window on an object store is a window during which DELETED user content stays readable** - weigh that against what the window buys; it is not free time.
- **The database cannot tell you what REFERENCES a media object** - an attachment id travels inside the ciphertext, so "is this blob still needed" is answered from the migration record, never from a query.
- **Before deleting a volume, MOUNT it and ask it** - a throwaway container over the volume costs 30 seconds and is the only measurement that postdates the decision.
- **A volume outlives the compose file that named it** - every deleted service owes an explicit `docker volume rm`, and there is usually more than one.
- **A HOST-SIDE PORT OFFSET MUST NEVER APPEAR IN A CONTAINER-TO-CONTAINER ADDRESS.** Inside a compose network a service answers on the port it LISTENS on; the number left of the colon in `ports:` exists only on the host and is invisible to peers. `docker-compose.dev.yml` offset every port so a second stack could share a machine, applied the offsets to the internal URLs as well, and pointed four of them at closed ports - for four months, with nothing reading it. `.github/scripts/tests/compose-wiring.test.sh` now derives each service's listening ports from the file and holds every address against them.
- **ADDING A PROXY HOP MAKES A SERVER PARSE ITS OWN OUTPUT, AND HEADERS GET A BUFFER OF THEIR OWN.** `proxy_buffering off` streams the BODY; response headers are read into `proxy_buffer_size`, one page by default. A header a server GENERATES is never measured against that limit - it is only measured when something reads it back - so a configuration that worked for years answers `502` the day a second hop appears. This estate's CSP is ~1.5 kB and did exactly that.
- **A HEALTH CHECK MUST FETCH WHAT A USER FETCHES, NOT THE CHEAPEST ROUTE THAT ANSWERS.** The 502 above left every page broken while the container stayed HEALTHY, because the probe asked for `/api/version` - the one route that sets no CSP, chosen originally *because* it was cheap and unauthenticated. A probe picked for its cheapness is a probe selected for not resembling the traffic. Fetch a real page too.
- **AND THE OFFSETS THEMSELVES WERE UNNECESSARY** - a compose project already gets its own network and its own volumes, and production publishes NO host port for an internal service, so there was nothing to collide with. Before offsetting anything, check whether the thing being avoided is published at all.

## Shared gotchas -> [development](development.md), [cicd](cicd.md)

Environment and tooling traps that belong to no one subsystem. Each cost a run.

- **A SWITCH IS NOT A MECHANISM, AND AN ENABLED TIMER IS THE MOST CONVINCING WAY TO HAVE NEITHER.** On 2026-09-03 all four hosts answered `apt-daily-upgrade.timer: enabled` and not one had `unattended-upgrades` installed; `mitv` went further and carried `APT::Periodic::Unattended-Upgrade "1"` with the package absent - a configuration that reads as ON and does nothing at all. Anyone auditing that estate by listing timers would have concluded packages were current while one box was 113 behind. **So ask what RAN, never what is enabled**, which is the same rule this file already carries about GitHub's cron arriving late or not at all: a schedule is a request, and its failure mode is absence. Two corollaries, both measured the same day. **An APT configuration LIST accumulates across files rather than overriding**, so declaring `Unattended-Upgrade::Origins-Pattern` APPENDS to the package default - the resolved policy on the trixie boxes opened with `label=Debian`, the whole of stable, while the file said security; `#clear` first, then state it, and note that bookworm and trixie ship different defaults so a config verified on one is not verified on the other. **And a scope is worth verifying rather than arguing**: the fear priced in the backlog was that unattended upgrades would restart Docker and reproduce a 30-second `502`, and `--dry-run --debug` showed the Docker CE origin pinned `-32768`, *"Marking not allowed"* - the cost simply was not incurred. [host-updates](infrastructure/host-updates.md)
- **AN ENUMERATION OF WHAT SOMETHING TOUCHES IS A SECOND, SILENT STATEMENT OF IT - ask the system
  instead.** `bump-version.yml` staged an eleven-line `git add` list beside a script that writes
  those same files: two statements, nothing comparing them, so a new manifest or a renamed directory
  would be bumped on disk and left out of the commit - a release whose components disagree, surfacing
  at a store upload rather than in CI. `git add -u` cannot drift because it asks git. The general
  form: when a list must track a behaviour, prefer deriving it; when it cannot be derived, a TEST
  must compare the two copies. And prefer the narrow derivation - `-u` (tracked modifications) over
  `-A` (anything present) - because the wide one is a behaviour change wearing a simplification's
  clothes. See [cicd](cicd.md#version-bump).

- **A BOT'S PUSH OBEYS THE SAME RULESET A HUMAN'S DOES, AND THE ACTIONS APP CANNOT BE EXEMPTED FROM
  A REPOSITORY RULESET.** `GITHUB_TOKEN` acts as `github-actions[bot]`, which is not a bypass actor
  unless somebody made it one - and it cannot be made one: GitHub answers `422 Actor GitHub Actions
  integration must be part of the ruleset source or owner organization`. So a workflow that pushes
  to a protected default branch needs an App installed in the ORGANISATION, whose installation token
  it mints per run. Two consequences to carry: an App-token push RAISES a `push` event where a
  `GITHUB_TOKEN` push does not, so check what listens on `push` before switching; and the failure
  mode of getting this wrong is silent in the reassuring direction - the run goes red and every
  downstream `workflow_run` gated on `conclusion == 'success'` simply never starts, which looks like
  "nothing happened" rather than like a fault. See
  [cicd](cicd.md#the-push-this-workflow-makes-is-the-one-push-to-main-that-is-not-a-pull-request-and-the-ruleset-refused-it-measured-2026-09-03).

- **CAPTURE A HOST'S FAILED UNITS BEFORE YOU CHANGE ITS STATE, or you cannot tell your damage
  from what was already broken.** Rebooting `mitv` on 2026-09-03 surfaced two failed units, and
  answering "were these mine?" took a trip through `journalctl --list-boots` and the previous boot's
  logs to prove they had failed identically since 9 June. That trip was avoidable: one
  `systemctl list-units --state=failed` beforehand settles it instantly, and without it a session
  either wastes the reconstruction or - worse - assumes. The same applies to container health and
  listening ports: the pre-check that reads cheap is the one that makes the post-check mean
  something. See
  [host-updates](infrastructure/host-updates.md#the-73-tb-raid1-nobody-was-watching-found-while-rebooting-for-the-kernel-2026-09-03).

- **AN ALERT DESTINATION THAT DELIVERS NOWHERE IS WORSE THAN A MONITOR THAT REFUSES TO START.** A
  failed unit is visible; a running unit posting into an unread spool reads as health. `mdmonitor`
  on `mitv` wanted a `MAILADDR` on a box with no active MTA and a `monit` carrying no alert
  destination - supplying one would have turned a loud failure into a silent one over 7.3 TB of
  RAID1. Send the event where somebody or something actually looks, and when nothing does, say so
  in the repository instead of satisfying the daemon. And give the alarm SEVERITY BY EVENT CLASS: a
  level that fires on `RebuildFinished` is a level its reader learns to skip.

- **A CHECK THAT CANNOT READ ITS EVIDENCE REPORTS HEALTH, AND THAT IS WORSE THAN NOT EXISTING.** The host-update report's first real run said `last log outcome: never` on a box whose upgrade had finished four hours earlier: `/var/log/unattended-upgrades` is `root:adm 0750` and the reporting account was outside `adm`, so the ERROR arm was unreachable whatever the host did. The fix is two parts and only one of them is the permission. **"Cannot see" and "nothing happened" must be DIFFERENT VALUES**, and the unreadable one must be a finding that names the group - otherwise the day somebody removes it, the report goes quiet instead of going red. The same run also invented a finding from the opposite direction: the facts file was written unquoted and read with `.`, so an `origins=a|b` line was parsed as a PIPELINE, the variable came out unset, nothing errored, and a perfectly correct host was accused of allowing no origins at all. Anything a shell will source gets `%q`. Both arms are pinned in `host-update-report.test.sh`, which exists because **a report whose verdict has never been seen to FAIL is the same defect one level up.** **AND GRANTING THE PERMISSION IS NOT APPLYING IT: a process holds the group set it was STARTED with.** `adduser` returned success, `id -Gn` listed the group at once, and the next run was still blind - the long-lived service had `Groups: 27 100 991 1000` with no `4` in `/proc/<pid>/status`, while a fresh `ssh` session had it. A restart of the service is part of the change, not a follow-up to it. That accident is also the best thing that happened to this report: it was **proved able to fail against the real box** - red because it could not see, green after the restart, nothing else about the host having changed. [host-updates](infrastructure/host-updates.md)
- **A RENAMED HEADING BREAKS EVERY LINK INTO IT AND NOTHING ANYWHERE REPORTS IT.** GitHub does not 404 an unresolvable fragment: it serves the page scrolled to the top, so a reader following a link to a section that no longer carries that name lands on a 900-line file with no idea which paragraph was meant - and the page still LOOKS right to whoever renamed the heading, because the link lives somewhere else. In a repository whose own index tells you to read the wiki before the source, that is the difference between a pointer and a maze. Found 2026-09-03 by sweeping all 98 markdown files: two dead anchors, one created that same day by renaming a `cicd.md` section during the workflow migration, one dead for far longer with nobody noticing. `.github/scripts/tests/wiki-links.test.mjs` asserts every intra-repository link resolves - file AND anchor - and **`.md$` is in `ci.yml`'s `run-scripts` trigger for the reason that decides the shape of every derived test here: the commit that breaks the link touches only the page being renamed, so any narrower trigger passes on exactly the commit that breaks it.** Getting the SLUG right is what makes it believable rather than deleted: markdown links slug as their label, `_` survives, and each space becomes one `-` - collapsing whitespace reported a dozen live links as dead on the first run. [cicd](cicd.md)
- **AN IGNORE RULE FOR A SECRET FILE DOES NOT COVER THE BACKUP YOUR OWN TOOLING WRITES BESIDE IT, AND THIS REPOSITORY IS PUBLIC.** The root `.gitignore` listed `.env`, `.env.local` and `.env.*.local`; a new script kept the previous environment as `infrastructure/.env.bak`, which matches none of them, and `git add -A` staged 7930 bytes of production credentials. Caught in the commit, before the push, by reading what was staged - nothing else would have said so. **`frontend/.gitignore` already had the correct rule** (`.env.*` with `!.env.example`), so the repository disagreed with itself about the same question and the weaker half was the one that mattered. Two rules follow: when a tool starts writing a NEW file next to a secret, the ignore pattern is part of that change; and when two ignore files answer the same question differently, the answer is the stricter one. [development](development.md)
- **A WORKAROUND FOR A MISSING CAPABILITY BECOMES A DEFECT THE MOMENT THE CAPABILITY ARRIVES, AND NOTHING ANNOUNCES IT.** Three services exempted the ESM-only `uuid` from `transformIgnorePatterns` so ts-jest would rewrite it into CommonJS - the only way jest could load it at all. Enabling `--experimental-vm-modules` did not make that exemption unnecessary, it made it WRONG: jest now resolves `uuid` through its ESM path and evaluates the rewritten file as a module, where `exports` does not exist. The suite died on `ReferenceError: exports is not defined` in a dependency nobody had touched. **When you add a capability, enumerate what was compensating for its absence** - the compensations are not inert, they are code that was correct only against the old constraint. [nestjs-framework](services/nestjs-framework.md)
- **AN ENV-VAR PREFIX IS SHELL SYNTAX, AND `node --run` OPENS NO SHELL - so a flag a child process needs belongs on `argv`.** `ci.yml` runs these suites with `node --run test`, which executes the `package.json` script directly; `NODE_OPTIONS=--experimental-vm-modules jest` works perfectly under `bun run`, is silently inert under `node --run`, and the difference shows up only as the CI failure the local run could not reproduce. Writing the flag into the command - `node --experimental-vm-modules node_modules/jest/bin/jest.js` - is also what gets it to jest's WORKERS, which inherit `process.execArgv` and not a prefix somebody set upstream. **Ask of every flag both questions: does the runner interpret the syntax, and does the process that actually needs it inherit the value.** [nestjs-framework](services/nestjs-framework.md)

- **AN EDGE ERROR CODE IS AN HTTP RESPONSE, SO "DID I GET A STATUS CODE" ACCEPTS THE FAILURE.** A probe written as "anything that is not `000` means the tunnel routed it" passes a wall of Cloudflare `530`s - which is the edge saying it could not reach the origin at all, i.e. exactly the failure being tested for. The same trap holds for `502`. **Compare against the codes the endpoint gave BEFORE the change**, host by host: seven hostnames answering `200 200 302 200 200 302 302` before and after is a verdict, "they all answered something" is not. Take that baseline before touching anything, because after the change there is nothing left to compare with. [cloudflare-edge](infrastructure/cloudflare-edge.md)
- **A COMMAND'S OUTPUT IS LOCALIZED AND YOUR PATTERN IS NOT - so export `LC_ALL=C` BEFORE PARSING IT, on every host you did not configure.** Two measurements of the same box were wrong the same way: `apt-cache policy cloudflared | sed -n 's/^  Candidate: //p'` read EMPTY, and `apt list --upgradable | grep -c upgradable` read 0. That host's apt answers in French - `Candidat :`, and a translated word where `upgradable` was expected - so both parsers found nothing and both nothings were reported as facts: "no Cloudflare repository is configured" and "nothing is pending". The repository was configured, the candidate was there, and one package WAS pending. **A grep that finds nothing looks exactly like a system with nothing to find, which is why this class of error gets believed and written down.** So: force the locale, and be suspicious of any zero that arrives from a machine whose language you never checked - especially an appliance, which is where a non-English default is likeliest. [cloudflare-edge](infrastructure/cloudflare-edge.md)
- **AN ENABLED TIMER IS NOT A MECHANISM, AND IT READS LIKE ONE.** The production host had `apt-daily-upgrade.timer` `enabled` with `unattended-upgrades` NOT INSTALLED and no `20auto-upgrades` config - so the timer fired and upgraded nothing, for as long as anyone cares to check, while an audit that listed timers would have concluded packages were current.
